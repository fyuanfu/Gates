Discovery Gap 消除方法研究

1. 核心结论

AI 加持后的需求评审，真正有增量价值的部分，不是继续做“句子写得好不好”的检查，而是把过去高度依赖资深 Reviewer 经验的需求缺口探索变成可重复、可规模化的工程过程。

核心定义： Gap Discovery 不是“证明需求完整”，而是系统性扩大候选需求空间，并找出当前 Requirement Set 无法回答的重要关注点。

AI 的优势

高 Recall、快速扩展候选空间、可并行从多视角探索、可重复执行。

人的优势

掌握真实业务语义、优先级和组织约束，能提供最终业务 Oracle。

推荐组合

AI 扩展搜索空间 + Evidence 约束 + Human Confirm，而不是 AI 单独批准需求。

2. 什么是 Discovery Gap

需求文档中有两类不同的问题：

类别关注点例子
Defect Detection已经写出来的 Requirement 是否存在歧义、冲突、不可验证等缺陷。“系统应快速完成上传”中的“快速”没有阈值。
Gap Discovery需求空间中是否存在重要但当前文档尚未定义的场景、状态、异常、约束或假设。“用户可修改绑定手机号”，但未说明旧号码不可用、新号码已绑定、并发修改、会话失效等行为。
 
Known Requirements
        +
Candidate Requirement Space
        ↓
Compare / Coverage Analysis
        ↓
Unanswered Concern
        ↓
Candidate Gap

因此，Gap Discovery 最难的不是文本解析，而是：Candidate Requirement Space 从哪里来，以及怎样避免无限发散。

3. AI Gap Discovery 的评审目标

不应该把目标定义为“证明 Requirement 100% 完整”。自然语言需求没有一个可计算的完备性证明机制，AI 也没有天然业务真值。

更合理的目标： 在开发开始之前，系统性提高重要需求缺口的发现概率，并把尚未解决的不确定性显式化。
需求上下文
→
系统化探索
→
Candidate Gaps
→
Evidence
→
Human Oracle
→
确认 / 拒绝 / 补充

最终关心的不是“文档质量分数”，而是：

  • 是否仍存在会导致开发产生重大不同理解的未解决问题；
  • 是否存在关键场景、状态或失败行为没有定义；
  • 是否还有重要假设只存在于人的脑中；
  • AI 提出的高价值候选缺口是否已被确认、拒绝或转化为新 Requirement。

4. 为什么 Gap Discovery 比普通 Requirement Lint 难

难点原因后果
缺失内容不可直接观察文本中没有出现的东西，无法像模糊词一样直接匹配。必须先构造“可能应该存在什么”。
缺少天然 Oracle模型不知道真实产品规则。AI 的合理建议不等于真实缺陷。
搜索空间巨大场景、状态、角色、异常、数据、依赖、NFR 都可以无限扩展。容易产生 Candidate Explosion。
领域依赖强同一行为在支付、相册、社交、内部工具中的重要性完全不同。通用模型常识不够。
Completeness 无法直接证明“没有继续发现问题”不等于“没有问题”。应使用风险与覆盖证据，而不是绝对完整声明。

6. Discovery Gap 的六类主要消除方法

6.1 LLM 作为外部知识源：Candidate Concept Expansion

让模型利用语言和领域常识，推断当前需求上下文中通常还会出现哪些相关概念、行为或条件，再与 Requirement Set 比较。

Requirement Set
      ↓
Context / Concept Extraction
      ↓
LLM predicts related concepts
      ↓
Candidate concepts
      ↓
Compare with existing requirements
      ↓
Potential missing concepts

价值：发现显式文本之外的可能关注点。
主要风险：噪音大；通用常识未必适用于当前产品。

6.2 RAG + Domain Evidence：用领域资料约束模型

把纯模型常识替换为“模型 + 当前系统证据”，从相关需求、历史规则、领域文档、既有测试、相邻 Feature 中检索上下文，再生成候选缺口。

Current Requirement
       ↓
Retrieve relevant evidence
 ┌─────┼────────┬──────────┐
 │     │        │          │
历史需求 业务规则 相邻Feature  测试/缺陷
 └─────┼────────┴──────────┘
       ↓
      LLM
       ↓
Evidence-grounded Candidate Gaps

核心收益：降低 hallucination，提高与真实系统的相关性。

6.3 Scenario Generation as Probing：用场景反推需求缺口

与其直接问“还漏了什么”，不如要求 AI 构造可验证场景，再检查需求是否能够对每个场景给出确定答案。

Requirement
   ↓
Generate candidate scenarios
   ↓
Happy / Failure / Boundary / Recovery / Concurrent ...
   ↓
Can the requirement set determine expected behavior?
          ┌──────────┴──────────┐
         Yes                    No
          ↓                      ↓
      Covered               Candidate Gap

这是非常适合工程落地的 probing 方法，因为“生成场景”比“自由寻找一切遗漏”拥有更明确的搜索目标。

6.4 Cross-Pollination：Human 高 Precision + AI 高 Recall

工业研究显示，一个有价值的组合模式是分别让人工分析者和 LLM 展开需求，再与生产阶段真实产物或后续确认结果对比。其核心启发不是 AI 取代 BA，而是双方互补：

优势弱点
HumanPrecision 高、领域判断强Recall 容易受经验、时间、认知盲区影响
LLMRecall 高、探索快、容易发现 implicit/non-obvious concerns会生成不适用或过度设计的候选项
推荐定位：AI 扩大搜索空间，人负责收敛真值。

6.5 Cross-Artifact Discovery：从已有 Artifact 的关系缺口找问题

这是相对高可靠的一类 Gap，因为不是凭空创造需求，而是在已有工程对象之间寻找结构断点。

Goal → Requirement → Acceptance / Test / Design / Risk
                     ↑
                 Missing link
                     ↓
               Candidate Gap

典型问题包括：Requirement 没有验收条件、关键需求没有测试覆盖、依赖没有来源、父子需求关系断裂等。

6.6 Interactive Elicitation：AI 主动追问

把静态 Review 变成动态需求访谈。AI 围绕尚未定义的行为主动提出问题：

  • 如果 X 失败怎么办？
  • 用户处于 Y 状态时，这条规则是否仍成立？
  • A 与 B 同时发生时谁优先？
  • 这里默认依赖了什么前提？
  • 这个行为是否在所有角色、设备或账户状态下一致？

AI 适合作为 Question Generator / Elicitation Partner，不适合作为 Business Oracle。

7. 关键工程原则：Bounded Gap Search

一个万能 Prompt ——“请找出所有遗漏需求”——看似覆盖面最大，实际最容易失控。更可靠的做法是把开放式搜索拆成多个受约束的探索任务。

Scenario Explorer

正常流程、替代流程、取消、中断、恢复、多角色场景。

State Explorer

前置状态、状态转换、非法状态、终止状态、恢复状态。

Failure Explorer

超时、失败、部分成功、重试、幂等、依赖不可用。

Boundary Explorer

最大/最小值、空值、重复、容量、时序、临界条件。

Rule / Constraint Explorer

业务规则、权限、优先级、互斥、约束、例外。

Dependency Explorer

上下游、接口、数据源、外部系统、配置、环境依赖。

NFR Explorer

性能、可靠性、安全、兼容、资源、可恢复性。

Assumption Explorer

隐含前提、默认业务事实、组织规则、时序与一致性假设。

上述 Explorer 是一种工程分解建议，用于限制搜索空间和提高可重复性；它不是某个统一国际标准中的固定八类 taxonomy。

其核心原则是：

不要： Requirement → "Find everything"

而要： Requirement → bounded perspective
                    → candidate concerns
                    → compare
                    → gap

8. Candidate Gap 的正确生命周期

AI 提出的“合理问题”不能直接叫 Defect。Gap Discovery 必须有一个显式确认过程。

Candidate Concern
→
Evidence Check
→
Open Question
→
Domain Owner
→
Confirm / Reject
→
Requirement / Finding

例如：

AI:
"手机号修改后，现有 session 是否需要失效？
在当前 Requirement Set 中未找到明确规定。"

此时状态：
Candidate Gap / Open Question

产品确认：
A. 全部失效
B. 当前设备保留
C. 全部保留

确认后：
→ 补充 Requirement
→ 或记录“不适用/无需定义”的决策
禁止模式：AI 根据常识说“系统应该怎样”，然后直接把自己的建议标记成 Major Defect。没有业务 Oracle 时，这只是 Candidate Concern。

9. Gap Discovery 的核心权衡：Precision vs Recall

Gap Discovery 很适合按信息检索问题来理解：

  • Recall：真实重要缺口里，AI 找到了多少；
  • Precision：AI 提出的候选缺口里，真正成立的有多少。
策略结果风险
只输出 100% 确定问题Precision ↑，Recall ↓失去 Gap Discovery 的主要价值
无限发散找所有可能性Recall ↑，Precision ↓Reviewer 被大量噪音淹没
受约束探索 + Evidence + Human Confirm在 Recall 与 Reviewer 成本间取得平衡需要设计过滤、排序和确认机制
推荐 KPI 优先级：首先关注重要缺口召回率，同时控制单位真实 Finding 所产生的候选问题数量，而不是单纯追求“AI 判断准确率”。

10. 推荐的工程化 Gap Discovery 流程

综合研究与工业实践，建议采用四阶段主流程：

1. Expand
→
2. Compare
→
3. Filter
→
4. Confirm

阶段 1：Expand — 扩展候选需求空间

  • 选择一个 bounded perspective；
  • 结合领域 RAG / 历史需求 / 相关测试 / 缺陷 / 业务规则；
  • 生成 Candidate Scenario / State / Failure / Constraint / Assumption。

阶段 2：Compare — 与 Requirement Set 对照

  • 判断现有需求是否已经明确回答该关注点；
  • 区分 Covered / Partially Covered / Unanswered；
  • 提供引用位置或搜索证据，而不是仅凭模型印象。

阶段 3：Filter — 去重、过滤、风险排序

  • 合并语义重复 Candidate；
  • 过滤明显超出 Scope 的建议；
  • 优先保留可能导致实现分叉、数据损失、安全风险、无法验收的问题；
  • 限制每轮输出数量，降低 reviewer fatigue。

阶段 4：Confirm — 交给领域 Oracle

  • 确认：转化为 Requirement / Finding；
  • 拒绝：记录不适用原因，避免下一次重复提出；
  • 暂不确定：保留 Open Question 和 Owner；
  • 结论反馈给后续 Reviewer，形成持续学习的领域上下文。

11. 如何评价一个 AI Gap Reviewer 是否真的有效

不能用“回答看起来聪明”来评估。建议建立可测 Benchmark。

11.1 Oracle / Benchmark 来源

  • Production-derived artifacts：用需求之后真正形成的用户故事、测试、设计、缺陷反推早期遗漏。
  • Seeded omissions：从完整需求集中人工移除已知场景或约束，测试 AI 是否能召回。
  • Expert Gold Set：由多名领域专家独立评审并仲裁形成基准。
  • Historical defects：将“因需求遗漏导致的历史缺陷”作为高价值 gap case。

11.2 推荐指标

指标说明
Critical Gap Recall高风险真实缺口被发现的比例；比全量 Recall 更重要。
Precision候选缺口最终被确认成立的比例。
False Positive Burden每确认一个真实问题，Reviewer 需要处理多少无效候选。
Novel Finding YieldAI 找到、而普通人工评审首次未发现的有效问题数。
Resolution Rate候选问题有多少最终被确认、拒绝或形成决策，而不是长期悬空。
Review CostAI 引入后总评审时间、人工确认成本是否下降。

12. Candidate Gap 推荐输出结构

输出必须能区分“证据明确的问题”和“待确认的候选缺口”。建议最小结构如下：

{
  "id": "GAP-017",
  "perspective": "failure",
  "requirement_refs": ["REQ-12", "REQ-13"],
  "candidate_gap": "上传过程中网络断开后的行为未定义",
  "why_it_matters": "开发可能分别实现为自动重试、立即失败或保持挂起",
  "evidence": {
    "searched_scope": "REQ-01..REQ-28",
    "covered_by_existing_requirement": false
  },
  "status": "open_question",
  "confidence": "medium",
  "suggested_owner": "product/domain owner",
  "resolution": null
}

推荐状态至少区分：

candidateopen_questionconfirmed_gaprejectedresolved

13. 当前 AI Gap Discovery 的能力边界

AI 可以扩大未知空间，但不能凭自身常识提供最终业务真值。
可以让 AI 做不应直接让 AI 做
从多个视角系统展开候选场景宣称需求已经“绝对完整”
结合 RAG 找类似规则、场景和历史证据凭常识决定真实业务政策
识别 Requirement Set 无法回答的问题把所有合理建议直接判成缺陷
发现 traceability / coverage 结构断点在无人工确认下自动批准复杂 Feature
生成高 Recall Candidate Gaps以质量总分代替关键问题 Gate

14. 最终结论

AI 时代需求评审最值得建设的能力，不是“自动把 Requirement 改写得更标准”，而是把需求未知空间的探索工程化。

Requirement Set
      ↓
Bounded Exploration
      ↓
Domain / Artifact Evidence
      ↓
Candidate Requirement Space
      ↓
Compare
      ↓
Candidate Gaps
      ↓
Filter & Rank
      ↓
Open Questions
      ↓
Human Oracle
      ↓
Confirmed Finding / New Requirement / Rejected
      ↓
Updated Requirement Set
一句话总结： Gap Discovery 的正确目标不是让 AI “证明没有遗漏”，而是让 AI 以高 Recall 系统性暴露可能遗漏的重要问题，再通过证据和人的业务判断把候选空间收敛成高 Precision 的 Requirement Set。

落地时最值得坚持的五条原则

  1. Search before Judge：先扩大候选空间，再判断是否成立。
  2. Bounded before Open-ended：分视角探索优于万能 Prompt。
  3. Evidence before Assertion：Candidate Gap 必须说明现有需求为何无法回答。
  4. Question before Defect：缺少业务 Oracle 时先标记 Open Question。
  5. Recall + Human Precision：让 AI 与人的能力互补，而不是相互替代。
