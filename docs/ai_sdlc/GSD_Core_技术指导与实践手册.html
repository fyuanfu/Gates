01. GSD Core 是什么

用框架视角理解它解决的问题与不解决的问题。

GSD Core（Git. Ship. Done.） 是运行在 AI 编程工具之上的 上下文工程 + 规范驱动研发 + 多 Agent 编排框架。它不是新的代码生成模型，不是独立 IDE，也不是把所有研发步骤放进一个永不清空的对话。

上下文工程

重任务转交具有新上下文的专职 Agent；主 Agent 仅负责调度和状态。

规范驱动

把项目、需求、决策、计划、验证结果存为长期有效的结构化文件。

可验证交付

执行结束不代表完成；将可验证的 must_haves、自动检查与 UAT 纳入闭环。

解决三个典型问题

上下文腐化（context rot）：长会话内容积累导致早期约束与代码事实被稀释；会话失忆：重启后难以承接之前的设计决策；执行即完成的假象：代码写出后缺乏独立核验和缺陷闭环。

源码确认
GSD 的官方阶段闭环是 Discuss → (可选 UI design) → Plan → Execute → Verify → Ship；部分版本还提供可选的 spec-phase，位于 discuss-phase 之前。不要把这套生命周期误解为“所有阶段都是强制自动执行”。

核对依据：↗ README↗ Context engineering↗ The phase loop

哪些是关键闭环？

计划校验循环

Research → Plan → Plan-checker → 修订。阻断型问题应在 Execute 之前被发现。

执行依赖循环

依赖图按 Wave 执行，同一 Wave 理论上允许并发，任务完成后写 SUMMARY。

缺陷闭环

Verify / UAT → 发现差异 → 诊断 → Gap Plan → Execute --gaps-only → 复验。

区分两类验证
不要混淆 VERIFICATION.md 与 UAT.md：前者偏向目标、must_haves、文件与连接证据的验证报告，后者是用户可观察行为的交互验收记录。两者可能在不同子流程生成或被消费。

08. Skills 组合场景与执行策略

6 个常用工作流方案以及最容易混淆的命令辨析。

下面将每个场景拆成“入口选择→连续 Skills→关键产物→异常回退”，这是技能全景图和技术卡片之间的桥梁。所有代码是参考操作序列，不是必须全部执行的脚本。

场景 01

A 已有 Android 工程：从知识抽取到需求验证

已有 Android 工程；核心是先确认现状，再锁定需求与方案，避免直接让 Agent 写代码。

bash
/gsd-onboard
/gsd-map-codebase                 # 首次完整映射；若 onboard 已完成可跳过
/gsd-spec-phase 1                 # 需求较复杂时：规则、状态、并发和禁止行为
/gsd-discuss-phase 1              # 确认技术决策与限制
/gsd-plan-phase 1 --tdd           # 测试义务先落到 Plan/Verify
/gsd-execute-phase 1
/gsd-code-review 1 --depth=deep   # 高风险更推荐
/gsd-verify-work 1
/gsd-ship 1
证据链： PROJECT / Codebase Map → SPEC / CONTEXT → RESEARCH / PLAN → commits / SUMMARY → UAT / VERIFICATION → PR

关键注意：实际需求语义不能从 Codebase Map 自动推出；重点审查状态转移、错误恢复、幂等约束与真实 Android 设备验证。

场景 02

B 完整需求交付：可选分支如何接入主线

在需求 WHAT 明确后，不同场景可插入 UI、AI、外部审查等子流程。

bash
/gsd-spec-phase 2
/gsd-discuss-phase 2
/gsd-ui-phase 2                  # 有 UI 时才运行
/gsd-ai-integration-phase 2      # AI 系统时才运行
/gsd-plan-phase 2
/gsd-review --phase 2 --codex    # 可选独立计划评审
/gsd-plan-phase 2 --reviews      # 若评审发现问题，带反馈修订
/gsd-execute-phase 2
/gsd-verify-work 2
证据链： SPEC → CONTEXT → UI-SPEC/AI-SPEC（按需）→ PLAN ↔ REVIEWS → Code → UAT

关键注意：不需要为了完整性机械执行所有可选 Skill：例如普通后端接口无需 ui-phase 与 ai-integration-phase。

场景 03

C 验收失败：从问题证据回到修复验证

真实行为没有满足预期，不能直接将 Phase 判为完成。

bash
/gsd-verify-work 3
# UAT 记录问题与诊断；必要时运行：
/gsd-debug --diagnose "异常行为描述"
/gsd-plan-phase 3 --gaps
/gsd-execute-phase 3 --gaps-only
/gsd-add-tests 3
/gsd-verify-work 3                # 必须复验，再判断是否 Ship
证据链： UAT 失败项 → Root Cause → Gap PLAN → 修复代码 / 测试 → 新 UAT/VERIFICATION 证据

关键注意：不要将“修了代码”视为缺口关闭；应检查测试失败方向、负向样例、版本签名和真实端到端行为。

场景 04

D 知识持续积累：代码、关联图与实践经验

希望以后新需求规划能复用代码架构、历史取舍和已确认问题。

bash
/gsd-map-codebase
/gsd-map-codebase --query status # 需 intel.enabled=true
/gsd-graphify build              # 需 graphify.enabled=true
/gsd-extract-learnings 3         # 从已执行阶段提取经验
/gsd-docs-update --verify-only
/gsd-map-codebase --query diff   # 变更后检查信息新鲜度
证据链： Codebase 7 文档 + 可选 Intel / Graph + LEARNINGS + 可信文档检查

关键注意：这不是预先存在的统一业务知识图谱；领域实体、需求/Scenario/代码/测试的溯源关系需要额外建设。

场景 05

E 快速任务与并行计划：不要过度设计

细小任务不一定进入完整 SDLC，大型并行任务则应维护明确的隔离与依赖。

bash
/gsd-fast "修复说明文档拼写"             # 一句话、小范围
/gsd-quick "更新同步错误文案"          # 保留计划/提交追踪

关键注意：当涉及跨模块状态、兼容性、用户隐私和不可逆发布行为时，不宜使用 gsd-fast 或不带验证的 quick。

场景 06

F 发布与质量回溯：Milestone 完成不等于命令无报错

/gsd-validate-phase 3             # 测试覆盖复核

/gsd-complete-milestone v1.0
/gsd-milestone-summary v1.0
/gsd-cleanup

  7. 映射基线盖章：工作流通过 gsd_run stamp-codebase-map 写入 last_mapped_commit 与 last_mapped_at。
  8. 泄密扫描 & 提交：检测常见 token/私钥模式；发现疑似秘密时暂停提交，正常情况下提交代码库映射文档。

16. 测试、验证、Gate 与质量证据

区分“计划存在”“测试通过”“行为被证实”。

Plan Quality

计划阶段：需求覆盖、任务完整、依赖、关键链接、可执行验证命令。

Implementation Evidence

执行阶段：任务提交、构建/测试、SUMMARY 中的结果与偏差。

Behavior / UAT

验证阶段：自动证据、用户可观察行为、待人工验证与缺口。

概念目标相关载体易发生的错误
Acceptance Criteria用户可观察、可判断的需求接受条件REQUIREMENTS / SPEC验收语义未明确
Task acceptance_criteria任务完成的局部判据PLAN把代码存在当功能生效
must_haves.truths最终必须为真的行为事实PLAN → VERIFICATION缺少运行时证据
must_haves.artifacts必需的文件或实现产物PLAN → VERIFICATION文件存在但未连接
must_haves.key_links组件/层之间的关键连线PLAN → VERIFICATION新增接口未被调用
Verification证明预期与实际一致VERIFICATION / tests只凭 Agent 自述通过
UAT从使用者角度检查交互UAT“能编译”代替“能用”

值得重点检查的诚信约束

VERIFICATION 的状态值以 passed、gaps_found、human_needed 为官方闭集。没有相关测试却依赖运行时行为成立的 truth 不应凭静态代码被当成已经验证；缺少足够证据的非可推断检查可能要求人工验证。SUMMARY 在具有 coverage 字段时还可指导哪些 UAT 可以由已通过的测试支撑，哪些需要人工判断。

推荐的人工抽检清单

  1. 能否从一个 REQ-ID 追到具体 PLAN task、代码和验证？
  2. verify 是否真的执行且能区分通过/失败？
  3. 是否有跨模块、重试、并发、错误恢复之类的未覆盖行为？
  4. 风险（CONCERNS）是否反馈到了方案和验证？
  5. VERIFICATION、SUMMARY、UAT 的结论是否一致？
应用建议
GSD 的验证机制能显著规范 AI 软件交付，但其质量上限仍受需求 Oracle、测试设计、真实运行环境与外部证据约束。不能把“Agent 检查通过”等同于生产级质量保证。

核对依据：↗ Verification 产物定义↗ Verify skill↗ Gate predicate

19. 自己使用时的审查模板和规范

可复制的工程审查条目；非官方强制要求。

A. Map 文档审查卡

markdown
# Codebase Map Review（团队自定义）
- Snapshot: git SHA / mapped_at / path scope
- Findings: 事实 / 推断 / 未知 分开记录
- Evidence: 每个关键事实附真实路径 + 代码区间
- Completeness: 七文档是否存在；重要业务模块是否覆盖
- Freshness: 与当前 HEAD 的代码变化是否相关
- Security: 是否包含密钥、内部账号、隐私数据
- Ownership: 谁确认这批知识可用于后续规划？

B. 需求 → 证据追踪的推荐数据结构

yaml（增强设计示例）
requirement_id: SYNC-AC-03
statement: 网络恢复后未完成照片应自动继续上传
source_ref: prd/gallery-sync.md#AC-03
scenario_id: SC-NET-RECOVERY
invariant_id: INV-NO-DUPLICATE-ASSET
code_anchors:
  - path: app/src/main/java/.../SyncWorker.kt
    symbol: SyncWorker.doWork
test_obligations:
  - id: TO-NET-RECOVERY-01
    precondition: 有一个未完成的同步任务
    action: 断网后恢复网络
    oracle: 最终成功且同账号照片不重复
    evidence_required: integration_test + device_test
status: candidate
应用建议
以上的 requirement_id / scenario_id / invariant_id / test_obligations 结构是推荐扩展格式，不是 GSD 内置的 schema。它展示如何把 GSD 的文件知识进一步变成可审计的业务语义证据链。

建议先用原生 gsd-map-codebase 做一期验证，再对一个有状态转换与异常边界的模块构建结构化知识抽取 PoC：重点评估正确召回率、事实可追溯、变更后漂移发现率、漏场景发现增益，而不是只比较生成文档的篇幅。
