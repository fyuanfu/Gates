Software Exploration Space

软件探索空间：一种用于系统发现需求、设计与验证盲点的方法

软件文档不应该把所有问题空间都写成章节；但软件分析过程必须有办法系统地发现“还没有被想到的问题”。本文提出一个“探索空间 → 相关性筛选 → 场景化 → 决策落盘 → 验证闭环”的方法，用来降低需求、设计和测试中的系统性遗漏。

1. 为什么需要“软件探索空间”

软件研发中最难的问题，往往不是“已经写出来的需求是否正确”，而是还有哪些本应被考虑的问题根本没有进入文档、设计和讨论。

传统文档评审很容易陷入一种局部正确性检查：

需求写了什么？
→ 设计有没有实现？
→ 测试有没有覆盖？

但如果需求本身就没有描述：

状态恢复 并发冲突 超时 依赖失败 生命周期 兼容性 权限差异

那么后续的设计和测试完全可能“正确地实现一个不完整的问题定义”。

软件探索空间的目标，不是让文档更长，而是建立一个用于发现盲点的坐标系：我们还应该从哪些相互不同的角度继续看这个系统？

2. Scenario、Flow 与“空间”的关系

2.1 Flow 不是 Scenario

Flow回答的是：事情如何按步骤、分支、循环、中断和恢复展开。它暴露的是路径空间。

Scenario回答的是：在某组具体前置条件下，发生某个动作后，系统应该产生什么可验证结果。它更接近某条具体路径上的行为实例。

Flow Start ↓ 选择照片 ↓ 格式合法？ ├─ 否 → 提示错误 → End └─ 是 ↓ 上传 ↓ 上传成功？ ├─ 否 → 重试/失败 └─ 是 → 保存 → 展示

对应的 Scenario 可以是：

Given 合法照片 + 网络正常
When 用户点击上传
Then 上传完成并展示成功

也可以是：

Given 上传已经开始
When 网络中断
Then 上传进入失败态
And 用户可以重试
关键结论：Flow 更像“路径生成器”，Scenario 更像从路径空间和其他问题空间中选出的一个可验证实例。

2.2 Scenario 不是独立的基础空间

更准确地说，一个有价值的 Scenario 往往是多个维度交叉后的结果：

Actor = 普通用户 Flow = 上传照片 State = 上传中 Data = 100MB 图片 Time = 长时间延迟 Concurrency = 同时上传两张 Dependency = 云服务慢响应 Environment = 弱网 Lifecycle = App 切后台 ↓ 形成一个具体、可验证的 Scenario

因此，Scenario 不是“和 Flow、State、Data 并列的另一个建模维度”，而更像是这些维度的组合切片。

3. 核心探索空间模型

下面给出一套适合作为软件分析“检查坐标系”的工作模型。它不是行业标准章节模板，而是一组用于防遗漏的分析视角。

3.1 基础问题空间

空间核心问题主要暴露的遗漏
Goal / Intent为什么做？真正目标是什么？目标错位、伪需求、局部最优
Actor / Role谁在做？不同角色是否有差异？权限、责任、角色行为差异
Flow事情如何展开？分支、循环、中断、恢复、遗漏路径
State系统可能处于什么状态？非法状态、遗漏状态、错误状态转换
Rule什么条件下允许、禁止、必须？业务约束、前置条件、不变量
Data有哪些对象、字段、边界、关系？空值、边界值、组合、数据一致性
Time时间和顺序如何影响行为？超时、延迟、过期、乱序、竞态
Concurrency多件事同时发生怎么办？重复执行、丢更新、死锁、竞态
Lifecycle对象、组件、任务如何创建、暂停、销毁、恢复？重建、恢复、后台化、资源清理
Dependency依赖什么外部系统或组件？超时、失败、部分成功、降级、重试
Interface / Contract边界之间如何约定？Schema、错误码、版本、契约不一致
Environment在哪些运行环境下工作？网络、设备、OS、区域、语言、配置差异
Resource资源受限时会怎样？内存、CPU、存储、连接数、电量、容量问题

3.2 横切质量空间

一些维度不是某个具体业务对象的结构，而是跨越所有基础空间的质量约束：

Reliability失败后是否可恢复？是否会丢失、重复、损坏？
Security认证、授权、信任边界、数据保护是否正确？
Performance延迟、吞吐、容量、资源成本是否满足目标？
Compatibility / Evolution升级、迁移、旧数据、旧客户端、灰度是否可控？
Observability系统出问题后能否通过日志、指标、Trace、证据定位？
可以把这套模型理解为一个“13 + 5”的工作模型：13 个基础探索空间 + 5 个横切质量空间。数字本身不重要，重要的是维度之间尽量正交，并能够稳定地暴露不同类型的遗漏。

4. Risk Pattern 的正确位置

Risk Pattern 很重要，但它不适合作为和 Flow、State、Data 完全同一级的基础空间。

原因是：一个风险模式往往会横切多个空间。例如“重复执行”：

重复执行 Risk Pattern ├─ Flow：同一步骤重复进入 ├─ State：状态重复转换 ├─ Data：重复写入 ├─ Concurrency：两个请求同时执行 └─ Dependency：下游重试造成重复调用

因此更合理的定位是：

基础空间用于展开问题结构；Risk Pattern 用于对这些空间进行失败模式投影。

这两者结合时，探索效果比单独使用风险清单更强：

基础空间
  ×
历史缺陷 / 风险模式
  ×
当前领域知识
  ↓
生成更高价值的探索问题和 Scenario

5. 为什么软件文档不应该按这些空间逐章展开

如果这些空间都重要，一个自然疑问是：为什么成熟的软件文档很少有 18 个章节？答案是：因为“思考结构”和“文档结构”不是一回事。

5.1 探索模型负责防遗漏

它回答：

还有哪些维度没有被考虑？
哪些维度与当前 Feature 有关？
哪些维度中存在未决问题或风险？

5.2 文档结构负责降低认知负担

最终文档更可能只写：

1. 背景与目标
2. 关键用户流程
3. 核心设计
4. 数据 / 接口
5. 异常与恢复
6. 关键决策
7. 验证与发布

State、Concurrency、Dependency、Lifecycle 等内容可以被折叠到这些章节里，只在有重要决策时显式展开。

错误做法：要求每个 Spec 都必须有 State、Concurrency、Topology、Security 等固定章节。这样很容易把探索模型变成文档形式主义。
更合理的原则：空间模型负责防遗漏，文档结构负责表达最重要的决策。

5.3 没有单独章节，不等于没有建模

问题空间常见承载物
Flow流程图、Activity Diagram、Use Case Flow
StateState Machine、状态表
RulePRD、AC、决策表、Invariant
DataER Diagram、Schema、数据字典
InterfaceAPI Spec、OpenAPI、IDL
Time / InteractionSequence Diagram、时序约束
SecurityThreat Model、安全设计
PerformanceSLO、NFR、容量模型

6. 软件探索空间的工程化使用流程

Step 1 明确目标与对象 ↓ Step 2 扫描基础探索空间 ↓ Step 3 判断哪些空间与当前问题相关 ↓ Step 4 对相关空间做交叉探索 ↓ Step 5 用 Risk Pattern / 历史缺陷做失败模式投影 ↓ Step 6 形成关键 Scenario ↓ Step 7 为关键 Scenario 明确 Oracle / Test Obligation ↓ Step 8 只把重要决策、约束、风险和证据落到文档

6.1 第一步不是“问完所有问题”，而是筛选 Relevant Spaces

一个简单的本地设置开关，可能只需要：

StateRulePersistenceCompatibility

而支付、同步、上传、消息系统可能必须考虑：

FlowStateTimeConcurrency DependencyLifecycleReliabilitySecurity

因此，空间模型应该是自适应选择，而不是全量强制展开。

6.2 真正有价值的是“交叉探索”

单独看 Data、State、Time 往往只得到局部问题；高价值问题通常产生于维度交叉：

交叉典型问题
State × Time一个状态停留太久后应该怎样？是否过期？
State × Concurrency两个事件同时试图改变同一状态时谁胜出？
Dependency × Retry × Data重试会不会造成重复写入？是否幂等？
Lifecycle × Flow流程执行中组件被销毁，回来后如何恢复？
Actor × Rule不同角色在相同业务规则下权限是否一致？
Environment × Performance弱网、低端设备下是否仍满足关键体验目标？

7. 如何用于 Gate1 / Spec Review

Gate1 不应该检查“有没有某个章节”，而应该检查：当前 Feature 相关的问题空间是否被充分识别，并且关键决策是否已经明确。

7.1 不检查 Presence，检查 Coverage

不推荐 是否有 State 章节？
是否有 Concurrency 章节？
是否有 Dependency 章节？
推荐 是否存在重要状态空间？若存在，是否被建模？
是否存在并发风险？若存在，行为是否已决策？
外部依赖失败时，产品和系统行为是否明确？

7.2 Gate1 应重点发现三类缺口

缺口含义示例
Coverage Gap相关问题空间完全没有进入讨论支付流程未考虑超时和回调乱序
Decision Gap问题被发现了，但行为没有决策“上传失败可重试”，但重试次数、幂等行为未明确
Verification Gap已经定义行为，但没有可验证 Oracle 或证据要求“性能良好”无法判定通过/失败

这样，Gate1 从“文档格式检查”升级为“问题空间与决策闭环检查”。

8. 示例：图片上传 Feature

8.1 初始需求

用户可以从相册选择图片并上传到云端。

如果直接进入设计，很容易得到一个只覆盖 Happy Path 的方案：

选择图片 → 调用上传接口 → 上传成功 → 展示结果

8.2 使用探索空间展开

空间可能需要探索的问题
Flow选择、裁剪、压缩、上传、保存、展示之间有哪些分支？
Stateidle / preparing / uploading / success / failed / cancelled 是否足够？
Data超大图、损坏图、HEIC、透明图、重复图片怎么办？
Time上传超时后，如果服务器稍后返回成功，客户端如何处理？
Concurrency同时上传多张图片时是否允许并发？最大并发数？
Lifecycle上传中 App 进后台、进程被杀、旋转屏幕后如何恢复？
Dependency对象存储成功，但业务服务保存失败，如何补偿？
Environment弱网、无网、蜂窝网络、漫游下行为是否不同？
Resource低内存设备处理大图是否 OOM？是否需要分块？
Reliability失败后重试是否幂等？会不会生成重复记录？
Observability如何区分客户端失败、上传服务失败、保存失败？

8.3 最终并不需要 11 个文档章节

探索后，真正落盘的文档可能只有：

1. Goal & Scope
2. Upload Flow
3. Upload State & Recovery
4. Data / API Contract
5. Error Handling & Retry
6. Lifecycle Handling
7. Verification & Rollout

这体现了本文最重要的原则：

探索空间可以很多，但文档只保留有决策价值的结果。

9. 实施原则与边界

原则 1：空间不是章节 不要求文档逐一对应，而要求相关问题被思考和决策。
原则 2：先筛选，再深入 不对每个 Feature 全量展开所有空间。
原则 3：关注交叉，不只关注单维度 高风险问题往往来自 State × Time、Dependency × Retry 等组合。
原则 4：Scenario 是结果，不是起点 先展开问题空间，再形成高价值 Scenario。
原则 5：Risk Pattern 是横切投影器 用历史缺陷和失败模式挑战已有模型，而不是代替基础建模。
原则 6：最终必须形成可验证闭环 关键行为需要 Oracle、Test Obligation 与 Evidence。
需要避免的误区：把“软件探索空间”变成新的重型模板。如果每个项目都要求机械填写 18 个维度，这套方法会迅速退化为形式主义。

最终模型

软件目标 / Feature ↓ 基础探索空间 Goal · Actor · Flow · State · Rule · Data · Time Concurrency · Lifecycle · Dependency · Interface Environment · Resource + 横切质量空间 Reliability · Security · Performance Compatibility/Evolution · Observability + Risk Pattern / 历史缺陷 / 领域知识 ↓ 识别相关空间 ↓ 交叉探索 ↓ 关键 Scenario ↓ Oracle / Test Obligation ↓ Decision / Evidence ↓ Gate Verdict

一句话总结：软件探索空间不是为了让软件文档写得更复杂，而是为了让软件团队和 AI Agent 在进入设计、编码和验证之前，有一个系统方法去发现“还没有被问到的问题”。
