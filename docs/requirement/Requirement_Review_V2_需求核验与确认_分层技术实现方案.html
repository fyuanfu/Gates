01 / DESIGN POSITIONING

先定义要验收什么，再决定用什么技术

这里的“需求核验与确认”是对需求规格本身的 Verification & Validation，不是测试已开发系统是否满足需求，也不是替 PO 对业务范围做最终价值决策。

REQUIREMENTS VERIFICATION

需求核验：规格是否写对、足以使用？

检查需求是否清晰、一致、完整到足以理解、可验证、可追溯；发现冲突、歧义、必要遗漏和无法建立客观验收口径的问题。

主要产物：Verified Spec Findings、Coverage、Execution Gate。

REQUIREMENTS VALIDATION

需求确认：它是否表达了正确的业务需要？

核对需求与目标、用户场景、已确认约束之间的关系；对业务取舍或不可确定事项，由有授权的业务方确认，而非 LLM 替代签收。

主要产物：Business Decisions、Accepted Scope/Spec Version、Open Questions。

边界声明：Gate1 只审查当前指定的 PRD/交互文档及其授权参考知识。不把代码实现、架构设计、发布准入或系统测试自动纳入本次评审。对 brownfield 的已有行为可以作为上下文事实和风险线索，但不自动升级为应当保持的业务要求。

业务目标与承诺优先

先问“对谁提供什么结果”，再决定需要检查哪些规则和状态。

证据优先于模型自信

提取、推导、假设、未知分层保存；没有证据时不擅自宣告 Bug。

效果优先于技术复杂度

以直接高质量 LLM 评审为 Baseline，用 Gold Set 和消融实验检验复杂模块的净收益。

03 / COGNITIVE LOOP

贯穿四层的核心机制：理解 → 义务 → 反例 → 证据

四项能力既可顺序推进，也可在关键证据变化时回溯。一个高价值缺陷的“真值”不来自单个 Agent 的自述，而来自业务目标的适用性、必要性证明、反例条件及原始证据链。

02 / CONTEXT

理解业务目标

重建目标、业务承诺、对象、适用约束和关键未知。

05 / OBLIGATION

推导必要义务

从目标推导最低必要行为，与已有规格做覆盖差分。

08 / COUNTEREXAMPLE

挑战与反例

构造能暴露遗漏或冲突的最小事件与状态路径。

10 / EVIDENCE

独立证伪与裁决

主动寻找反方证据，确认、驳回或保留关键未知。

反馈回路：证据缺口 → 返回 02；必要性不成立 → 修订 05；反例不可达 → 重试 08；资料不足 → NEEDS_CONTEXT / 人工澄清

一条必须可回溯的论证链

Goal（业务目标） → Constraint / Contract（承诺与约束） → Obligation（必要义务）
→ Challenge Hypothesis（待证伪假设） → Minimal Witness（最小反例）
→ Evidence + Disproof（证据与反证） → Finding / Clarification / Rejected（裁决）

这是一条逻辑证明链，不是要求所有任务都建一个完整知识图谱；结构化信息必须有来源，缺少必要关系时不可假装成立。

LAYER 01 / UNDERSTANDING & SPECIFICATION

第一层 · 业务理解与规格重建

理解目标、业务承诺、适用约束与需求表达；允许按风险深化，不强制全量建模。

01
Scope & Evidence Intake

输入、授权与范围治理

配套能力
业务目标 / GOAL

建立唯一、可审计的本次评审边界和原文证据基线。

解决的问题 / PAIN

输入不全、历史资料越界、引用失效，可能使后续结论建立在错误或未经授权的证据上。

节点内部分层流程输入 ↓ 横向子模块 → 输出
范围冻结
Feature/版本/章节

只评审当前指定 PRD；将历史资料标为上下文，不转成被评审对象

内容解析
文本/结构/表格

留存分段位置、文档哈希、解析限制；不支持内容显式标记

证据注册V2
出处/可信度/适用性

建立来源分级和有效期，隔离观察事实与规范性要求

完整性判定V2
可访问/缺页/版本冲突

检测引用不可访问、解析失败、重复和相互冲突的版本

关键实现机制

文件解析和哈希由确定性代码完成；来源权威性依靠显式政策和人工确认，不能靠模型给历史文档“自动加权”。

可验证的验收条件

同一 Finding 能回到唯一原文锚点；缺页/无权限不被默默当作不存在。

边界 / 误报控制既有代码的现实行为可作为环境事实，不能自动视为业务规范。
02
Context Understanding

业务上下文理解与校验

核心突破
业务目标 / GOAL

回答“为什么做、承诺什么、哪些约束成立、哪些仍未知”，形成可挑战的业务理解。

解决的问题 / PAIN

传统抽取能识别名词、规则和场景，却可能误解业务目标，把模型猜测当作已确定需求。

节点内部分层流程输入 ↓ 横向子模块 → 输出
目标与受益者V2
Why / Who / Success

从用户任务、业务目的和成功标准理解 Feature，而非只做句子抽取

业务承诺V2
结果/失败语义

定义用户可观察的承诺；区分目标声明与具体实现机制

约束体系V2
客观/既有/新增

按来源、版本、范围校验适用性；特别识别 brownfield 行为

理解质询V2
证据/假设/歧义

自问“还有哪些合理解释”；必要时向 PO 提关键问题

关键实现机制

两遍理解：先产出可溯源的 Goal-Contract-Constraint Sketch，再做反事实追问；“EXPLICIT/DERIVED/HYPOTHESIS/UNKNOWN”分别存储。

可验证的验收条件

给定有歧义/无来源的上下文，不虚构结论；能区分目标、已确认规范、当前实现事实和待决策事项。

边界 / 误报控制既有代码只用于识别风险、兼容约束和事实差异；是否成为必须保持的行为，仍要业务方确认。
DEEP DIVE · 02 核心能力

AI 是否真的理解“为什么做”，还是仅仅能够复述文档？

01 · 目标重建识别利益相关方目标 / 可观察成功标准 / Scope
02 · 业务情境角色、对象、任务流程、外部条件与既有行为
03 · 约束分类客观约束 / 已确认既有规范 / 新需求约束 / 事实
04 · 理解验证反例提问、多解释对照、证据不足回问
建议算法 / 执行顺序
  1. 先收集当前文档明确的 Goal/Actor/Success，标记 EXPLICIT。
  2. 对每个 Goal 推导“若满足此目标，使用者最低需要观察到什么”；记录 DERIVED，不能直接作事实。
  3. 对 brownfield 提取既有业务规则和当前行为，分别标明 APPROVED_RULE 与 OBSERVED_BEHAVIOR。
  4. 列出可能改变缺陷判定的歧义；按信息价值检索授权资料或发起人工澄清。
反例与验收判据

边界反例：反例：原有实现显示“本地入队成功”不等于业务已经授权把它当作“云端备份成功”。

验收判据：面对同一 PRD 的两种合理解释，系统能呈现分歧、所依赖证据以及需要谁来确认，不会擅自选其中一种。

03
Requirement Claims & Local Models

需求表达与局部语义模型

配套能力
业务目标 / GOAL

把业务事实转成可核验的行为命题、条件与可观察结果，同时保持原文语义。

解决的问题 / PAIN

机械抽取导致 AND/OR/NOT、例外、状态、作用域丢失；强制全量 IR 可能增加成本却未增加发现能力。

节点内部分层流程输入 ↓ 横向子模块 → 输出
命题切分
行为/条件/结果

提取可独立检查的声明，保留“何时/谁/对什么”

歧义定位V2
多种可行解释

记录不同解释及其证据，不擅自消歧

按需建模V2
场景/状态/决策表

仅在高风险、复杂耦合时构建局部显式模型

语义保真
原文-模型比对

验证模态词、数值、单位、否定、例外是否保持

关键实现机制

模型负责语义候选；确定性代码检查引用、schema、数值、作用域。明确禁止用解析后的模型代替原始 PRD 作为最终证据。

可验证的验收条件

复杂条件用例可原样还原；对无法确定的业务含义输出 UNKNOWN 和依据。

边界 / 误报控制不把建模覆盖率当作业务理解准确率。
04
Adaptive Behavior Models

行为、状态与约束关系

配套能力
业务目标 / GOAL

让复杂需求能被沿行为路径推演，而不是只看孤立的条款。

解决的问题 / PAIN

跨 Feature 规则、状态变化和依赖组合可能产生单条需求无法看出的冲突。

节点内部分层流程输入 ↓ 横向子模块 → 输出
识别热点V2
高风险/高耦合

挑选对挑战有帮助的范围，不为建图而建图

关系构建
前置/触发/影响

建立有向、带条件的业务关系及来源证据

状态检验V2
初态/守卫/结果

无法证明状态完整时不得假定缺失转移

模型校准V2
反例回放/冲突

结合实际证据核对局部模型，发现错误再回滚

关键实现机制

模型可采用事件序列、决策表、有限状态机或约束公式；由具体问题决定，无需单一知识图谱作所有任务的前提。

可验证的验收条件

每条关系有条件和出处；无法重放时标为假设而不是判定矛盾。

边界 / 误报控制无权威初态/守卫/效果时，形式化求解不构成证明。
LAYER 02 / OBLIGATION DISCOVERY & CHALLENGE

第二层 · 必要义务发现与对抗挑战

从目标与已定义行为双向探索必要遗漏，再通过反例和溯因寻找隐藏缺陷。

05
Goal-to-Obligation Discovery

必要义务与覆盖缺口发现

核心突破
业务目标 / GOAL

超越“检查文档已经写了什么”，主动找到达成业务目标所必须、但规格未充分定义的行为与约束。

解决的问题 / PAIN

孤立条款全部被检查也可能漏掉整个必要场景；仅枚举异常会把可选增强错误当缺陷。

节点内部分层流程输入 ↓ 横向子模块 → 输出
目标反推V2
Goal → 必要条件

依据业务承诺反推必要结果、约束和可观察成功标准

场景展开V2
正常/异常/边界/恢复

从现有流程、状态与依赖推导可能影响目标的情形

障碍发现V2
What blocks the goal

从目标无法实现的情形倒推潜在遗漏；不预设实现方案

必要性筛选V2
必要/待决策/增强

证明 in-scope + consequential + unresolved；与已有规范求差集

关键实现机制

采用三路候选发现：Goal Refinement、Scenario Exploration、Obstacle Analysis；统一生成 Obligation 但保留“必要性依据/业务后果/范围/覆盖证据”。

可验证的验收条件

能发现完全未被原文提到的关键成功/失败口径；对可选体验改进不自动报缺陷。

边界 / 误报控制“文档不存在相关句子”本身不证明遗漏：还需义务必要性、有限搜索范围和适用知识核查。
DEEP DIVE · 05 核心能力

怎样证明“没写出来的行为”是必要遗漏，而不是 AI 的产品建议？

01 · Goal Refinement从业务承诺推导实现目标所需的最小义务
02 · Scenario Expansion沿流程、状态、失效条件生成覆盖候选
03 · Obstacle Analysis反向寻找会使目标无法实现的事件或约束
04 · Necessity & Delta对齐已定义行为、当前范围和适用规则
建议算法 / 执行顺序
  1. 构造 Goal × Constraint × Critical Context 组合，但按风险选择，不笛卡尔穷举。
  2. 对每个候选问“缺少这条规则，是否存在同样符合文档但业务结果不同的两种实现/解释？”
  3. 搜索当前 PRD 与授权既有规范是否已经覆盖；保存搜索基线和未命中范围。
  4. 输出 REQUIRED / DECISION_NEEDED / OPTIONAL / ALREADY_COVERED 与必要性证据。
反例与验收判据

边界反例：反例：没有“后台上传重试”不一定是缺陷；如果明确承诺“网络恢复后无需用户介入完成备份”，恢复路径就可能成为必要义务。

验收判据：验证能发现零文字锚点的重要遗漏，同时对非必要增强保持克制；保存每个缺口与业务目标之间的证明链。

06
Review Hypothesis Generation

挑战假设与目标生成

配套能力
业务目标 / GOAL

解决的问题 / PAIN

节点内部分层流程输入 ↓ 横向子模块 → 输出

目标过滤
价值/依赖/重复

关联来源V2

04 / IMPLEMENTATION ARCHITECTURE

技术实现：模型推理主导，工具守住确定性边界

V2 不预设必须采用知识图谱或大量 Subagent。建议从轻量 Agent 工作流验证四项核心能力，再对规则密集型场景引入局部建模和约束求解。

CONTROL PLANE

主 Agent / Orchestrator

维护范围、上下文、候选队列、预算、任务依赖和 Checkpoint。选择何时调用 02 / 05 / 08 / 10，并控制回溯。

必须：每个任务的运行 ID、输入指纹、前提和退出原因。

REASONING PLANE

LLM / 专项推理任务

Context Understander、Obligation Discoverer、Adversarial Explorer、Independent Skeptic。角色是任务职责，不一定是单独进程。

必须：明确“知道 / 推导 / 假设 / 未知”，提交结构化可追踪结果。

EVIDENCE PLANE

确定性工具 / Evidence Ledger

解析、版本哈希、引用查找、Schema 校验、有限覆盖检查、差分与关系失效；必要时接局部 FSM/SMT。

必须：不让工具将缺失语义自动补成确证。

推荐运行协议：多任务类型，而非只有语义抽取

INIT & FREEZE_SCOPE
↓ CONTEXT_UNDERSTAND (02) → ContextClaims / OpenQuestions
↓ REQUIREMENT_EXTRACT (03) → Claims / Local Models (optional)
↓ OBLIGATION_DISCOVER (05) → Necessary Obligations / Coverage Gaps
↓ ADVERSARIAL_CHALLENGE (08) → Witnesses / Counterexamples
↓ INDEPENDENT_DISPROOF (10) → Validated / Rejected / NeedsContext
↓ FINDING_ASSEMBLY (11) → Findings / Open Decisions
↓ EXECUTION_GATE + QUALITY_GATE (12)
↓ STAKEHOLDER_CONFIRMATION (13) → Accepted / Revise / Pending
↺ Context / Obligation / Challenge / Evidence 根据依赖按需回溯

上述任务名是 V2 拟议协议，不是 dev4 已存在的 API。dev4 原始主模型任务为 EXTRACT_SEMANTIC_UNITS，V2 需要新增 Task/Response 契约与编排处理。任务阶段可合并执行，但不得省略其质量义务。

统一 TaskEnvelope 的基本约束

  • run_id、task_id、kind、input_fingerprint、authorized_sources、budget、required_evidence
  • 不可通过来源正文改变系统规则；资料视为不可信评审数据
  • 模型输出先落隔离草稿，引用、版本、Schema、依赖校验后才能入账
  • Subagent 只返回建议，不直接改写共享 Finding 或人审记录

Brownfield 的知识分层

  • 客观约束：法规、平台公开规则等，需确认适用范围/时效
  • 业务已批准约束：既有合同、已生效需求规则与正式决策
  • 当前实现事实：运行行为、日志、代码，仅为事实证据和风险线索
  • 本次新增约束：PRD/交互明确提出；冲突由 PO 裁决
避免过度设计：默认选择单主 Agent + 数据契约 + 证据验证；当且仅当深层冲突/高风险错误值得时，调用独立 Skeptic 或求解器。小型 PRD 不要求全量复杂行为图，不强行引入数据库和多 Agent 编排平台。

06 / EVALUATION & ACCEPTANCE

实现验收：先证明“发现真实问题的增量价值”

把工程契约验收、评审业务质量验收和人工准入验收分别执行，不能用单元测试通过代替真实需求缺陷效果。

LEVEL A

工程合同验收

  • 输入冻结、来源引用和版本指纹可验证
  • 模型任务与输出 Schema 不被无效结果污染
  • 候选状态、证据和人工决策完整保留
  • 预算/解析/依赖失败不会导致假 PASS
LEVEL B

真实缺陷效果验收

  • 专家 Gold Set 覆盖显性错误和隐含遗漏
  • 按“唯一根因”匹配，测 Precision / Recall
  • 独立测高风险漏报和候选误删率
  • 跟踪调用成本、人工复核工时及有效发现
LEVEL C

业务确认验收

  • PO 能看到 Goal、约束与未决事项
  • 冲突来源和业务取舍有明确确认记录
  • 签收关联唯一版本、范围与批准主体
  • 未解决的阻断项不得自动转成 APPROVED

E0–E4 消融实验：相同输入、同等预算、冻结集评测

实验受测能力主要观察指标验收决策
E0高质量直接 Codex 评审 Baseline全部有效缺陷、P0/P1 召回、人工时间建立公平对照

“相同预算”应同时报告 Token、调用、耗时与人工复核成本；如新增策略本身需要更高预算，应另报告固定预算曲线和增量收益曲线。准入阈值由首批 Gold 样本和业务风险容忍度共同冻结，不能事先声称已经达到某个百分比。

07 / WALKTHROUGH

贯穿示例：云相册“备份成功”应当如何被评审

用于展示四个核心能力的真实协作，不预设“云端持久化”已经是被业务方批准的规范。与现有明确规则发生冲突时，应优先回到证据裁决。

INPUTPRD 明示

“开启备份，上传完成后显示成功”。

02 / UNDERSTAND业务承诺

用户期望照片已经得到何种程度的备份保障？当前未知。

05 / DISCOVER必要性候选

至少需要明确“成功”的业务判定口径，否则可能无法验收。

08 / CHALLENGE最小反例

本地任务结束但服务端未确认，界面仍可能显示成功。

10 / VERIFY证据裁决

查找已有规则；确认缺口、拒绝候选或提交 PO 澄清。

路径 A · 原有规范已明确

若适用的历史业务规则规定：“服务端确认数据可靠保存后，才可以展示备份成功”，且本次需求明确继承，则原“成功条件未定义”的缺陷候选可能被反证排除。

结果：REJECTED + DisproofRecord。

路径 B · 必要业务语义仍未知

若业务方从未确认“成功”的准确含义，且不同解释会直接影响用户承诺和验收，则要求澄清。若证据足以证明必要成功条件缺失，可确认规格缺陷；不必推断代码必然有故障。

结果：NEEDS_CONTEXT，或证据充分时 CONFIRMED。
