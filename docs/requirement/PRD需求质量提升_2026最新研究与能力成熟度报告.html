00 / EXECUTIVE FINDINGS

研究结论：技术已能“扩大发现”，但还不能“保证需求正确”

与自动驾驶技术评价类似，需求质量研究也应拆成可测试的能力目标，并明确运行设计域（Operational Design Domain）。单篇论文在有限数据集上的高分只代表该范围内的能力，并不意味着完整 PRD 可以实现自动验收。

FINDING 01 · 完整性

漏需求搜索从自由想象进入结构化领域覆盖

Cross-Pollination 用十类能力缺口搜索，在三个项目取得高于人工的召回率，但伴随严重“过度补全”；最终范围仍须由业务持有人确认。[R03]

FINDING 02 · 澄清

主动提问比模型独自理解更有价值

OntoAgent 把需求访谈组织为经验本体驱动的覆盖搜索；ClarifySTL 把欠规格和歧义拆开处理。二者在特定基准上有效，但尚未验证复杂PRD普适可靠性。[R04][R07]

FINDING 03 · 逻辑与验收

形式化可验证“给定约束”，无法证明“前提完整”

状态机、时序逻辑和SMT可在有限模型里定位反例；但语言到模型的忠实性与业务目标正确性仍需要外部Oracle。不能把 SAT 等同于“PRD正确”。[R07][R14]

FINDING 04 · 可开发门禁

准入门禁已出现研究原型，可靠校准尚未完成

RSGA 将需求充分性从检查意见升级为阻断条件；但真实PRD、多团队、长期误放行和误阻断数据仍不足，不能直接把论文阈值部署为统一政策。[R06]

总体结论

目前相对可落地的是：确定性结构检查、带证据的候选遗漏发现、主动澄清、追溯候选恢复以及可审计的人工门禁。当前仍不能实现的是：在开放业务世界中自动证明没有关键遗漏、自动判定真实业务价值、自动保证验收Oracle正确。

01 / GOAL DECOMPOSITION & EVIDENCE RULES

如何评价“已经达成到什么程度”？

先定义需求质量的使命：在明确的业务范围和风险约束下，交付“正确、完整、无关键歧义、内部一致、可验证、可演进”的需求集合，让开发、测试和发布决策获得足够证据。评价对象是整份PRD及其关联工件，而不是单条文字。

设计域（研究成立的前提）

必须同时标注：①输入工件类型（单句 / User Story / 完整PRD）；②业务领域（网页 / 电商 / 安全关键系统）；③上下文（是否有领域知识、界面原型、生产资产）；④Oracle（真实用户、生产实现、人工标注或规则模型）；⑤过程（离线批量、交互追问、人工审批）。越界时应降低评价强度。

“在受控Benchmark达到90%准确率”≠“在所有真实PRD有90%保障率”；“找到更多候选”≠“产品应该实现更多需求”。

双轴评价：成熟度 × 证据可靠性

技术成熟度 T0–T4 是对“可在真实PRD工程流程中重复实现的能力”的判断；证据等级 A–D 是评价结论可信程度，绝不混为一个分数。

A 标准/规范：定义应然要求，不证明自动化性能；B 同行评议+可检视数据：具备正式实验基础；C 预印本/有限原型：值得复现；D 本报告分析推断：必须通过后续实验确认。

T0 开放难题T1 方法/原型T2 特定基准有效T3 有条件工程可用T4 跨场景稳定验证
层级可满足的证据条件不能据此推断
T0尚无可靠的通用自动化解决方案，或目标本身需要无法从文本获得的外部真值。不等于数学上绝对不可能。
T1原理、概念验证、小样例或单一系统原型。不能声称适用于复杂真实PRD。
T2有明确基准、可定义指标和对照结果；可能仅局部子任务成立。不能推断现实多团队、跨领域稳定有效。
T3可构造确定性工作流，或存在有限真实项目证据；含人工复核和退出机制。不能声称已自主可靠。
T4多个独立团队、真实PRD、长期跟踪、误报漏报均达预设阈值，并可重复复现。不等于对开放业务世界的形式完备性证明。

说明：本报告没有把任何“开放业务语义理解”自动评为T4；T3主要指带人工监督的辅助性工程能力，决非完全自动化。

→

G6

把性能、安全、可靠性、隐私、可运维和质量权衡纳入真实范围。

多目标冲突已有研究 → 了解证据和边界
G7

可追溯性、依赖与演进质量

需求有出处、有相关依赖、能定位变更范围，并在版本演进中持续保持一致。

追溯链接提议可用 → 了解证据和边界
G8

开发充分性、门禁与可审计性

判断需求是否足以进入下一阶段，并以证据和责任人管理已知不确定性。

门禁原型已被验证 → 了解证据和边界
横向能力贯穿所有目标：证据可追溯、人工反馈、模型适用域、失效模式、成本与质量监控。质量不是“一次检查”的产物，而是每次范围变化后重新验证的状态。

目标 G1 · 能力边界

业务真实性与需求必要性

关键闭环未解决

确保“做什么”来自真实价值与被授权的业务意图，而非语言模型的合理想象。

为什么难

业务目标存在于组织决策与用户行为中，无法仅从PRD文本证明正确。

研究采用的方法

事实证据分层 → 利益相关方确认 → 假设/决策登记 → 变更与范围授权。

尚未解决的问题

推荐验收指标

被确认候选比例、无证据需求数、未经授权的范围扩展数、需求目标映射覆盖率

目标 G5 · 能力边界

为什么难

06 / EXECUTABLE REVIEW CASE

一个PRD如何经过“目标驱动的质量验证”？

以下是构造的教学案例，不是论文实验结果。以一个常见的交易产品需求说明从主流程出发怎样系统寻找隐含缺口、构建反例、明确Oracle。

PRD 原始描述

“订单创建30分钟后自动关闭未完成的订单，并通知用户。”

STEP 1 · 事实 / 未知区分

已知事实

  • 存在订单创建事件
  • 存在自动关闭行为
  • 30分钟是显式阈值
  • 存在通知用户的目标

未知：“未完成”是否等于未支付？计时基准、取消延迟与用户类型未定义。

STEP 2 · 场景补全

从10维提取候选缺口

  • 谁有权限取消，商家是否需要感知？
  • 支付成功、失败、处理中有哪些状态？
  • 30分钟边界的支付回调如何仲裁？
  • 异步任务失败如何恢复、重试是否幂等？
  • 通知发送失败后，业务是否回滚？
STEP 3 · 形式化检查

寻找最小逻辑反例

状态 = {CREATED, PAYMENT_PENDING, PAID, CLOSED} 约束A: PAID → 不能执行超时关闭 约束B: 未完成 AND elapsed≥30m → CLOSE 反例: PAYMENT_PENDING支付回调刚转PAID，同时超时任务读到旧状态

必须追问：状态读写是否原子？以何种事件时间为准？先成功提交哪种状态优先？这里只展示待建模的潜在冲突，并未运行SMT证明。

STEP 4 · 验收Oracle

转成可判定的规则

  • 给定订单已支付成功，执行过期扫描，不得产生超时关闭转移
  • 给定同一订单重复接收超时任务，最多产生一次合法的关闭业务事件
  • 给定通知通道失败，记录失败并按明确政策重试；不得悄悄篡改订单状态
  • 给定处理时延及并发竞争，确定唯一裁决规则

候选问题必须人工确认，而不是自动写回PRD

□确认“未完成”的业务定义
□确认超时从何时开始计时
□确认支付与关闭并发的优先级
□确认通知失败与订单状态解耦原则
□确认幂等、重复回调和补偿规则
□确认人工例外和责任人

目标：输出“已确认事实、候选遗漏、未决问题、冲突反例、验收义务、决策轨迹”六种独立对象。避免一次性生成无审查的大段“完美PRD”。

07 / OPEN SCIENTIFIC PROBLEMS

最值得继续研究的七个根本难题

01 · 真正完整性判据

如何定义“应该出现的需求全集”？即使召回率对生产系统很高，参照集可能本身漏需求。

  • 研究：有界领域本体、能力维度、闭世界假设
  • 需证明：上下文增量信息能否稳定提升Recall且不伤Precision

02 · 可信业务Oracle

模型用自己的理解给自己的生成打分，会形成自验证循环。

  • 研究：用户决策、合同规则、参考实现多源独立验证
  • 需证明：独立审查是否减少错误放行

03 · 精确语义与多模态一致

PRD中的文字、表格、流程图、设计稿经常表达相互矛盾的行为。

  • 研究：跨工件场景IR与证据对齐
  • 需证明：冲突定位精度和修订后语义保真

04 · 形式模型是否忠实

SMT可以精确分析模型，却不能保证模型正确转换了自然语言。

  • 研究：双向释义、专家抽检、符号/实例双验证
  • 需证明：模型抽取错误不会被“形式证明”掩盖

05 · 需求质量与真实缺陷因果关系

论文通常评价文字或抽取结果，缺少对后续生产缺陷和返工的长期关联。

  • 研究：跨版本对照、缺陷溯源和混杂因素控制
  • 需证明：高质量分数实际降低哪些缺陷类型

06 · 风险校准与门禁优化

统一阈值很容易牺牲效率，甚至阻断正确需求或放行高风险需求。

  • 研究：风险敏感阈值、置信区间、例外治理
  • 需证明：不同业务域下的误阻断与漏放行损失

07 · 持续变化与可复现评估

需求演进、模型升级、领域知识变化会使一次成功的评估快速失效。

  • 研究：稳定基准集、模型漂移监测、增量检查
  • 需证明：跨模型、跨团队、跨时间仍有稳定收益
核心认识论边界：任何有限、封闭的形式化模型都可以在其假设范围内进行穷尽检查；但现实产品需求所依据的用户目标、业务事实和未来环境通常属于开放世界。把“模型中没有发现反例”写成“业务需求没有缺陷”，属于不成立的推论。
08 / R&D ROADMAP

从研究结论到可验证工程能力：三个阶段

以下为建议的实施顺序，不是对论文团队发展时间的预测。每阶段都要求独立评测并明确退出条件，避免单靠“看起来聪明”的演示判定成功。

PHASE 1 · 0–3个月

建立可信评估基线

目标：先知道工具发现了哪些真实问题，损失了多少审查时间。

  • 抽取50–100份不同质量的历史PRD
  • 标注已知缺陷、允许范围、业务决策与反例
  • 建立10维缺口搜索、术语检查、报告溯源
  • 先采用人工批准，不自动修改PRD
准出：能复现实验、可计算Precision/Recall，关键误报可追溯。
PHASE 2 · 3–6个月

突破语义与场景质量

目标：减少“只会多问、不解决”的无效工作。

  • 加入领域经验本体的主动澄清
  • 状态/规则/边界模型与反例生成
  • 对高风险场景尝试有界SMT验证
  • 用户确认结果固化成可追溯Oracle
准出：验证反例的命中率、歧义关闭率及每项决策成本。
PHASE 3 · 6–12个月

形成证据化充分性门禁

目标：从“评审报告”转为可治理的研发准入能力。

  • 按风险对安全/一致性/可验证性设置门槛
  • 范围、假设、例外、责任人全链审计
  • 需求→验收→代码/测试候选关联
  • 追踪下游返工与缺陷，校准错误放行成本
准出：多团队真实使用，误放行/误阻断得到可解释改善。

投入优先级矩阵

优先级 P0｜已经值得工程化

来源与范围标记、确定性检查、10维候选缺口、异常/状态提醒、人工确认问题清单；低成本积累可信标注和反馈。

优先级 P1｜值得做有界研究原型

多解释澄清、领域经验本体、状态机与规则约束、可验证场景IR、风险敏感门禁；先限定业务域。

优先级 P2｜需持续实验后放大

跨PRD和UI的多模态语义一致性、变更多跳影响、独立Oracle生成、自动权衡非功能质量目标。

不应承诺为自动保证

开放世界“绝对无遗漏”、无需真人就能确定产品价值、只靠模型自检证明正确、统一分数对所有业务放行。

09 / BENCHMARK & VALIDATION PROTOCOL

如何真正验证PRD质量提升系统的价值？

真实样本集按领域/文档规模/缺陷类型分层
→
独立标注至少两名业务/技术评审
→
对照实验人工 vs 一次性LLM vs 结构化方法
→
缺陷复核争议集与范围外案例复审
→
下游追踪返工/缺陷/门禁误判

必须报告的主指标

Precision = 已确认且在范围内的问题 / 全部被提出的问题 Recall = 找出的真实问题 / 标注的真实问题总数 Critical Omission Rate = 漏掉的高危必要要求数 / 高危要求总数 Clarification Yield = 经确认有价值的决策 / 澄清总轮次 Gate False Release = 不应放行却放行的PRD / 不应放行的PRD

对于无法穷尽真值的真实项目，不应伪造Recall。可以用盲审抽样的估计区间、后续发现的逃逸缺陷和人工复核覆盖代替。

对照和可靠性要求

  • 样本按“普通需求、复杂状态、非功能高风险、跨系统依赖”分组。
  • 训练/知识库构建集与测评集隔离，避免历史PRD泄漏。
  • 固定LLM版本与Prompt/Skill版本，并提供完整运行证据。
  • 报告模型间方差、成本、耗时和人为复核负担。
  • 所有输出结论必须含输入证据锚点或说明无法确证。
  • 按高风险漏报分别报告指标，不能只用总体F1。

判定方式：测试目标是否被满足，而不是测试Agent是否会输出

研究问题正向实验负向/对抗实验通过意味着什么
找遗漏从原PRD删掉已知异常场景，看是否恢复加入“明确不支持”的诱饵功能同时保证Recall和Precision
澄清歧义注入同一句话两种真实可行行为加入表面复杂但确定无歧义的语句避免泛化误报，给出最小可回答问题
查冲突植入已知不可满足的状态/时序规则植入语义相近但其实兼容的规则反例有效且能解释真实矛盾
验收Oracle需求、测试条件、期望结果三方独立审核对期望值植入单点错误能够发现Oracle自身错误
门禁高危约束缺失时应阻断低风险缺字不应阻断全团队风险与误判成本可校准
研究成功判据

不是“模型补充了100条需求”，而是“在预先定义的风险与范围内，准确发现更多真实缺陷、让歧义更少、需求更可测试，并在可接受成本下显著降低下游缺陷或返工”。
