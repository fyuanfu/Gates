Gate2：Feature 开发完成后的工程准出方案

Feature 开发完成 → Gate2 → 用户 / UAT 验收
核心目标：在交给用户验收前，研发侧先完成一次“有证据的工程验收”
Gate2 不替代 UAT，也不重新做需求评审；它确认批准的功能意图已被实现、关键行为已被证明、变更风险处于允许范围、当前 Candidate 真正具备验收条件。

Gate2 最终只回答四个问题

Implementation
做对了吗？
批准的需求和设计是否被正确实现，是否存在漏实现、错误实现或语义偏差。
1
Verification
证明了吗？
关键需求行为是否存在有效测试，并在当前 Candidate 上形成可信 Evidence。
2
Safety
搞坏了吗？
本次 Diff 是否引入不可接受的回归、兼容、安全、接口或工程风险。
3
Readiness
能验收了吗？
当前 Candidate 是否能正常 Build、安装 / 部署、启动并通过 Critical Smoke。
4

总体实现链路

批准基线Spec / AC / Rule / Design
→
实际实现Diff / Code / Config
→
验证与风险检查Test / Impact / CI / Security
→
Evidence当前 Candidate 上的事实证据
→
Finding & VerdictPASS / BLOCK
相比传统门禁的变化： 不再只判断“Build/Test/扫描是否为绿”，而是进一步判断“Feature 是否做对、测试是否真的证明需求、是否存在遗漏风险”。

核心能力：LLM 扩大检查空间，确定性工具提供事实证据

LLM 负责语义理解、关联和风险发现；Build/Test/Scanner 等确定性工具负责可验证事实。

1 实现一致性检查｜做对了吗？

Spec / AC / Rule批准意图
↔

  • 代码行为是否与需求语义冲突
  • 是否偷偷改变已有行为
  • 重大设计决策是否被绕过

LLM 与确定性工具的职责边界

能力LLM 负责确定性工具负责最终原则
Requirement ↔ Implementation语义偏差、遗漏、跨文件逻辑问题Repository Fact / DiffLLM 发现问题，证据验证事实
Requirement ↔ Test测试缺口、Oracle 是否足够Test Execution / Result“有 Test”不等于“证明 Requirement”
Diff ↔ Impact影响范围与回归风险推理依赖图、调用图、既有 Regression风险未闭环则形成 Finding

核心原则：LLM 找问题，Evidence 定事实。 Gate2 不让单次 LLM Opinion 直接成为唯一 Hard Block 依据，而是把语义发现转化为可审计 Finding 和 Evidence。

落地方式：一个自动执行、不中断开发确认的 Gate2 Skill

执行过程中不人工逐条确认；Skill 自动完成检查、证据汇聚、Finding 验证和阻塞判定，最终一次性输出报告。

Finding 收敛为 6 类

Implementation Gap

要求与实际实现存在缺口。

Verification Gap

该证明的行为没有得到有效证明。

Regression Risk

变更可能破坏已有系统且风险未关闭。

Engineering Failure

Build、Static、Security、Contract 等确定性失败。

Evidence Gap

证据缺失、过期、错误版本或不可追溯。

Open Risk

已发现风险未关闭或未合法接受。

最终只保留 4 条最高层阻断策略

B1｜没有正确实现Required Feature Behavior 未实现或实现错误。
B2｜没有有效证明Required Behavior 没有当前 Candidate 上有效 PASS Evidence。
B3｜存在不可接受风险Build / Test / Security / Regression / Compatibility 风险超过阈值。
B4｜Candidate 不可验收Build / Install / Deploy / Smoke / Config 不满足验收条件。

一句话总结
Gate2 的核心不是再增加一轮测试，而是建立 “需求意图 → 实际实现 → 验证证据 → 风险 → 准出结论” 的自动闭环，让 Feature 在进入用户验收之前，研发侧先完成一次有证据的工程验收。
