基于 SDD 的 AI Agent 分层测试指导

指导 AI Agent 在 Spec-Driven Development 中，将 Small / Medium / Large Test 作为研发流程内生的验证机制，而不是代码完成后的补充测试。核心目标是建立从 Requirement、Design、Task 到 Evidence、Verdict 的可追溯质量闭环。

1. 目标与适用范围

本指导解决的不是“测试应该写多少”，而是 AI Agent 在基于 SDD 研发时，如何在正确的阶段产生正确的验证义务，并用最低成本、足够充分的测试范围给出可信证据。

核心问题：一个需求、一个设计决策、一个实现任务，到底有什么必须被证明？这些证明应该由 Small、Medium 还是 Large Test 提供？

1.1 适用对象

  • 基于 PRD / Spec / SDD / Technical Design 驱动的 AI Agent 开发。
  • Agent 负责规划、编码、测试、Review、验证中的一个或多个角色。
  • 希望把“代码生成”升级为“实现 + 验证 + 证据 + 判定”的研发系统。

1.2 不解决的问题

  • 不规定固定的 Small / Medium / Large 数量或比例。
  • 不要求每一个 Story 都机械地产生三种测试。
  • 不把测试类型等同于 Unit / Integration / E2E 的名称映射；Test Size 首先表达验证范围、依赖与执行成本。

2. 核心原则

原则 1：Test Obligation 先于 Test Case

Requirement / Design / Task │ ▼ “What must be proven?” │ ▼ Test Obligation │ ▼ 选择最小充分验证范围 │ ┌─────┼─────┐ ▼ ▼ ▼ Small Medium Large │ ▼ Executable Test │ ▼ Evidence → Verdict

原则 2：Oracle 不应由实现反向定义

禁止的自证循环：Agent 先写实现 → 再根据实现生成测试 → 测试证明实现正确。
这会让测试偏向“验证当前代码做了什么”，而不是“验证需求要求什么”。

原则 3：选择最小的充分验证范围

能用 Small Test 提供充分证据，就不升级到 Medium；能用 Medium 证明，就不依赖 Large。Large 应保留给必须经过真实系统链路、用户场景或运行环境才能判断的行为。

原则 4：测试是任务的完成条件，而不是任务后的补充工作

一个 Implementation Task 必须携带自己的 Verification Obligation。Task Done 的含义不是“代码已写”，而是“实现与要求一致，相关证据已经产生”。

原则 5：Verification 与 Implementation 应保持角色隔离

不要求一定使用不同模型，但至少要隔离角色、提示词和判断依据，使 Verification Agent 能独立从 Spec / Design / Obligation / Diff / Evidence 推导 Verdict。

3. 总体研发模型

Feature Intent │ ▼ ① SPECIFY Requirement / Story / AC │ Large Test Obligation │ ▼ ② PLAN / SDD Architecture / Component / Contract State / Data / Dependency │ ┌──────────────┴──────────────┐ ▼ ▼ Medium Test Obligation Small Test Obligation │ │ └──────────────┬──────────────┘ ▼ ③ TASKS Implementation + Verification Plan │ ┌──────────────┼──────────────┐ ▼ ▼ ▼ Small Task Medium Task Large Task │ │ │ ▼ ▼ │ ④ IMPLEMENT │ │ │ │ Code + Small Component + Medium │ │ │ │ └──────────────┴──────────────┘ │ ▼ ⑤ FEATURE VERIFY │ Large Test │ ▼ Small / Medium / Large Evidence │ ▼ ⑥ CONVERGE │ Final Verdict
研发系统的完成定义：Implementation 完成 ≠ Feature 完成。只有 Spec、Design、Implementation 与 Evidence 一致，Feature 才能被判定为 Accepted。

4. Small / Medium / Large 三层测试职责

Small Test

Code OracleFast Feedback

证明：局部实现单元是否正确。

主要来源：详细设计、业务规则、函数/类契约、状态转换、边界、异常处理、Invariant。

典型对象：Reducer、Mapper、Validator、UseCase 局部规则、纯逻辑模块。

Medium Test

Contract OracleIntegration

证明：一组相邻组件之间的设计假设是否成立。

主要来源：组件边界、接口/API 契约、数据契约、状态传播、错误传播、配置与依赖行为。

典型对象：Repository↔DAO、Client↔Server、ViewModel↔Repository、序列化与协议。

Large Test

User OracleFeature Evidence

证明：最终产品是否完成用户目标和关键场景。

主要来源：Story、AC、Scenario、User Journey、环境条件、真实系统行为。

典型对象：跨组件 Feature、关键用户路径、持久化、离线、真实设备/服务协同。

维度SmallMediumLarge
核心问题代码单元对吗？组件接得对吗？用户目标实现了吗？
主要知识来源Detailed Design / Code ContractArchitecture / Interface ContractRequirement / Story / AC / Scenario
最早开始设计设计后期 / Task 拆分Technical DesignSpec / Requirement
成为可执行测试实现开始时即可Test Double 或组件实现就绪后关键系统链路就绪后
反馈速度最快中等最慢
失败定位最强较强较弱
真实度最低中等最高

5. 三层测试如何融入 SDD 阶段

5.1 Specify：先产生 Large Test Obligation

Spec 阶段的目标不是写 UI 自动化脚本，而是确定用户级可验证 Oracle：Story / AC / Scenario 是否能够明确回答“最终什么现象说明需求实现成功”。

large_test_obligations:
  - id: L01
    covers: [S01, AC01]
    scenario: 收藏照片
    oracle:
      - 收藏操作成功
      - UI 显示收藏状态

  - id: L02
    covers: [S01, AC02]
    scenario: 重新进入照片
    oracle:
      - 收藏状态仍保持
Spec Gate：关键 Story / AC 无法产生明确 Large Oracle，说明需求尚未达到可验证状态。

5.2 Plan / Technical Design：产生 Medium Test Obligation

当组件边界、接口、数据、状态、错误和依赖被设计出来后，Agent 应主动识别 Integration Point，并为关键 Contract 生成 Medium Test Obligation。

medium_test_obligations:
  - id: M01
    interaction:
      - FavoriteRepository
      - Room
    verify:
      - saveFavorite 正确写入数据库
      - readFavorite 能读取保存结果

  - id: M02
    interaction:
      - FavoriteViewModel
      - FavoriteRepository
    verify:
      - Repository 状态变化正确映射到 UI State
Design Gate：关键组件交互无法写出 Medium Test Specification，通常意味着 Contract 仍不完整。

5.3 Task Planning：具体化 Small Test Obligation

Small Test 通常在 Detailed Design / Task Decomposition 阶段最清晰，因为此时具体实现责任已经落到 Class、Function、Reducer、Mapper、Validator 等单元。

small_test_obligations:
  - id: S001
    unit: FavoriteStateReducer
    cases:
      - unselected + FavoriteClicked -> selected
      - selected + FavoriteClicked -> unselected

  - id: S002
    unit: FavoriteMapper
    cases:
      - favorite=true -> Selected
      - favorite=false -> Unselected

5.4 Implementation：兑现 Small / Medium Evidence

Agent 在实现每个 Task 时，应首先读取与 Task 绑定的验证义务，并在局部闭环内完成编码和验证。

5.5 Feature Verification：兑现 Large Evidence

当 Feature 的关键系统链路具备后，再执行最初由 Spec 冻结的 Large Test Obligation。Small / Medium 全绿不能替代用户级验收。

6.1 三阶段成熟度

成熟度能输出什么依赖
Obligation必须证明什么需求、设计意图、风险
SpecificationGiven / When / Then、输入输出、Oracle稳定的 Requirement / Contract
Executable Test可运行脚本/代码测试框架、Fixture、Fake/Stub、实现或环境

6.2 Medium Test 的特殊要求

Medium Test 设计依赖的是“代码接口背后的 Contract”，而不是必须等代码实现完成。设计阶段至少应明确：

  • Input / Output
  • Error / Timeout / Retry 语义
  • Data Schema / Mapping
  • State propagation
  • Idempotency / Transaction semantics
  • Configuration / Dependency behavior

只有组件图而没有上述 Contract 时，只能识别 Medium Test Obligation，无法形成高质量具体 Test Case。

7. Task 必须形成验证闭环

不推荐：T01 Implement Repository → T02 Implement UI → T03 Add tests
在 Agent 场景下，这会天然导致测试后置，并放大“实现定义测试”的自证风险。

7.1 推荐的 Task 结构

task:
  id: T03

  implements:
    story: S01
    design:
      - FavoriteRepository

  obligations:
    small:
      - S001
      - S002
    medium:
      - M01

  implementation:
    - FavoriteRepository

  done_when:
    - code implemented
    - S001 passes
    - S002 passes
    - M01 passes

7.2 Coding Agent 局部循环

读取 Task │ ▼ 读取相关 Spec / Design / Obligations │ ▼ 建立或确认 Small Test │ ▼ 实现 Production Code │ ▼ Small Evidence │ ▼ 运行相关 Medium Test │ ▼ Self Review / Diff Review │ ▼ Task Complete

7.3 不要每个 Task 全量运行所有测试

Agent 应根据变更范围运行：

  • Direct Small Tests
  • Impacted Small Tests
  • Impacted Medium Tests

Large Tests 通常在 Feature 集成或关键节点运行。目标是在保证证据充分的前提下维持快速反馈。

8. Agent 角色分工

Spec │ ▼ Requirement Agent │ Large Obligations │ ▼ Design Agent │ Medium Obligations │ ▼ Task Planner │ Small Obligations │ ▼ Implementation Agent │ │ Small Code └─────┬─────┘ ▼ Review Agent │ ▼ Verification Agent │ │ │ Small Medium Large │ ▼ Final Verdict

8.1 Requirement Agent

  • 检查 Story / AC / Scenario 是否可验证。
  • 产生 Large Test Obligation。
  • 发现需求缺口时要求 Spec 补齐，不自行用实现假设填空。

8.2 Design Agent

  • 识别组件边界和 Integration Points。
  • 检查 Interface / Data / State / Error Contract。
  • 产生 Medium Test Obligation，并利用无法定义测试的地方发现 Design Gap。

8.3 Task Planner

  • 将实现责任拆成可闭环 Task。
  • 把相关 Small / Medium Obligations 绑定到 Task 的 done_when。

8.4 Implementation Agent

  • 不能自行改变已冻结 Oracle 来适配实现。
  • 执行 Task 级 Small / Medium 反馈循环。
  • 输出代码变更和对应测试证据。

8.5 Verification Agent

  • 输入：Spec、Design、Test Obligations、Code Diff、Test Evidence。
  • 独立判断实现是否满足上游要求。
  • 输出 Finding / Verdict，而不是替 Implementation Agent 解释失败。

9. 质量门禁设计

Gate检查对象核心条件主要 Test Evidence
Spec Gate Story / AC / Scenario 关键用户行为有可判断 Oracle Large Test Obligation 已定义
Design Gate Component / Contract / State / Data 关键 Integration Point 可验证 Medium Test Obligation / Specification 已定义
Coding Gate Task / Diff / Local Logic Task 自带验证闭环 相关 Small PASS；关键 Medium PASS
Integration Gate Component Interaction 设计中的 Contract 在真实组合中成立 Medium Evidence PASS
Feature Gate Story / AC / Scenario 用户目标真实成立 Large Evidence PASS
门禁不是“测试数量门槛”。不建议使用“Small ≥ 70%、Medium ≥ 20%、Large ≥ 10%”作为 Feature Ready 条件。应检查关键 Test Obligation 是否被充分覆盖，以及 Evidence 是否可信。

10. Evidence Chain 与最终 Verdict

最终验证报告应能从 Story 追溯到用户级、集成级和代码级证据。

Story S01：用户可以收藏照片 │ ├── AC01 │ └── Large L01 ✓ │ ├── AC02 │ └── Large L02 ✓ │ └── Design │ ├── FavoriteRepository ↔ Room │ └── Medium M01 ✓ │ ├── ViewModel ↔ Repository │ └── Medium M02 ✓ │ └── FavoriteStateReducer ├── Small S001 ✓ └── Small S002 ✓

10.1 推荐 Verdict 结构

story: S01
implementation: PASS
evidence:
  small: PASS
  medium: PASS
  large: PASS
gaps: []
verdict: ACCEPTED

10.2 Converge 的真正含义

Converge 不应只检查“是否漏实现”，还应检查：

  1. Implementation completeness：Spec 中要求的能力是否都有实现。
  2. Verification completeness：关键 AC / Scenario 是否都有 Large Evidence。
  3. Design verification completeness：关键 Contract 是否有 Medium Evidence。
  4. Code correctness evidence：关键规则、状态、边界是否有 Small Evidence。

11. Android Feature 示例：图片收藏

11.1 Requirement

Story：用户可以收藏图片，以便以后再次找到它。

  • AC01：点击收藏后显示收藏状态。
  • AC02：重新进入后收藏状态仍保持。
  • AC03：离线时仍可看到收藏状态。

Spec 阶段 Large Obligations：L01 收藏成功、L02 重进后持久化、L03 离线读取。

11.2 Technical Design

UI │ ▼ FavoriteViewModel │ ▼ FavoriteUseCase │ ▼ FavoriteRepository │ ▼ Room

Design 阶段 Medium Obligations：

  • M01：Repository ↔ Room，保存与读取一致。
  • M02：ViewModel ↔ Repository，收藏状态变化正确传播。
  • M03：重复收藏不产生重复记录。

11.3 Task / Detailed Design

Small Obligations：

  • S001：FavoriteStateReducer 的选中/取消状态转换。
  • S002：FavoriteMapper 的 Entity → Domain 映射。
  • S003：Storage Exception → Domain Error 映射。

11.4 实现与验证顺序

T01 定义 Repository Contract ↓ T02 建立 M01 Test Fixture ↓ T03 实现 Repository + S001/S002/S003 ↓ 运行 M01 ↓ T04 实现 ViewModel ↓ 运行 M02 ↓ T05 实现 UI ↓ 运行 L01 / L02 / L03 ↓ Verification Agent 生成 Story Verdict

12. 常见反模式

反模式为什么有问题正确做法
代码完成后统一“补测试” Oracle 易被实现污染，测试成为自证 Spec / Design / Task 分阶段先定义 Obligation
每个 Story 强制生成 Small/Medium/Large 忽略验证范围的实际需要，制造无价值测试 先问“必须证明什么”，再选择最小充分范围
只有组件架构图就直接生成 Medium Case 缺少 Input / Output / Error / State 等 Contract 先补足交互契约，再形成 Test Specification
每个 Task 全量跑所有测试 反馈变慢，Agent 迭代成本过高 Direct + Impacted Small / Medium；Large 在 Feature 节点执行
Small/Medium 全绿就宣布 Feature Done 不能证明用户目标成立 关键 Story 必须由 Large Evidence 做最终验收
Implementer 自己修改 Oracle 让测试通过 破坏独立验证 Oracle 变更必须回到 Requirement / Design 层重新评审

13. 落地检查表

13.1 Spec Ready

  • 关键 Story 是否有明确用户目标？
  • AC 是否能产生明确 PASS / FAIL Oracle？
  • 关键正常、异常、持久化、离线/恢复等场景是否被识别？
  • 是否已形成 Large Test Obligation，而不是提前绑定实现细节？

13.2 Design Ready

  • 组件边界和关键 Integration Point 是否明确？
  • 接口的 Input / Output / Error / State Contract 是否完整？
  • 关键数据映射、幂等、事务、重试、超时语义是否明确？
  • 关键组件交互是否能够形成 Medium Test Specification？

13.3 Task Ready

  • 每个实现 Task 是否绑定相关 Story / Design？
  • 关键逻辑是否有 Small Test Obligation？
  • Task 的 done_when 是否包含验证条件？
  • 依赖顺序是否支持先建立 Test Fixture / Contract 再实现？

13.4 Feature Ready

  • 相关 Small Tests 是否通过？
  • 关键 Contract 的 Medium Tests 是否通过？
  • 关键 Story / AC 的 Large Tests 是否通过？
  • Evidence 是否能从 Story → Design → Task → Test → Result 追溯？
  • 是否存在未关闭的 Finding / Test Gap / Known Risk？
  • Verification Agent 是否给出明确 Verdict？
最终定义：
AI Agent 基于 SDD 的分层测试，不是“Agent 自动生成三类测试”，而是让每一个 Requirement、Design Decision 和 Implementation Task 都携带相应的验证义务，并由 Small / Medium / Large 在最合适的层级产生可信 Evidence，最终支持 Feature Verdict。
