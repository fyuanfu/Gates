Gate1 Guidance

Gate1 Implementation Readiness 检查指导

用于 AI / LLM / Coding Agent 参与研发场景下的“进入实现前”质量门禁。

核心原则：检查对象、检查属性、Finding、Materiality 与 Verdict 必须分层，不在同一维度混用。

目标：Implementation Ready 模型：Object × Attribute 输出：Finding + Evidence 判定：PASS / WARN / BLOCK

1. Gate1 的总结性目标

Gate1 的目标不是“文档写完整”，也不是“消灭所有未知”。
Gate1 要确认：进入实现前，业务意图、关键行为、数据与契约、约束、技术方案以及验收定义已经达到足够明确、完整、一致、可实现、可验证、可追溯的状态， 使开发者或 Coding Agent 无需自行补充会显著改变产品行为、架构、安全、数据语义、上下游契约或验收结果的重要决策。

1.1 分层模型

L0 Goal为什么检查
L1 Object检查什么
L2 Attribute检查什么性质
L3 Finding发现了什么
L4 Materiality问题是否重大
L5 VerdictPASS / WARN / BLOCK

2. L1：检查对象

这一层只回答“Gate1 看什么”，不掺杂完整性、模糊性等质量属性。

一级对象二级对象核心问题
Intent & ScopeGoal / User / Scope / Out of Scope为什么做、为谁做、做到哪里、哪些明确不做。
BehaviorScenario / Flow / Rule / State / Edge / Failure系统在正常、异常、边界、状态变化等条件下应该怎样表现。
Data & ContractBusiness Object / Data Semantics / API / Dependency业务对象是什么、数据如何解释、上下游之间怎样约定。
ConstraintsArchitecture / Security / Privacy / Compliance / Platform / NFR实现必须遵守哪些技术、平台、安全、性能和组织约束。
Design / PlanSolution / Component / Key Decision / Implementation Plan关键技术方案是否足以支撑进入编码。
VerificationAC / Expected Result / Verification Approach / Evidence什么叫做正确，完成后拿什么证明正确。

3. L2：检查属性

这一层是横向质量维度。每一个重要检查对象，都应从这些属性上进行审视。

Completeness 完整性

必须知道的信息是否遗漏。核心问题：有没有缺关键定义？

Clarity 明确性

已有定义是否足够确定。核心问题：是否存在多种合理解释？

Consistency 一致性

不同定义是否互相冲突。核心问题：各处是否描述同一个世界？

Feasibility 可实现性

在真实约束下是否成立。核心问题：实际上能不能做？

Verifiability 可验证性

完成后能否客观判定。核心问题：怎么知道做对了？

Traceability / Coverage 可追溯与覆盖

关键定义是否被下游承接。核心问题：有没有丢失或无来源实现？

4. L3：详细检查矩阵（Object × Attribute）

LLM Gate1 的主要工作面应建立在这张矩阵上：先确定对象，再从属性角度查找 Finding。

检查对象 完整性 明确性 一致性 可实现性 可验证性 可追溯 / 覆盖
Intent / Goal 目标、用户价值、成功结果是否齐备。 目标是否存在多种业务解释。 与业务目标、产品定位是否冲突。 目标是否现实、可达。 能否判断目标是否达成。 是否被 Requirement / Story 承接。
Scope 范围、边界、Out-of-Scope 是否遗漏。 边界是否清楚，是否存在“顺手一起做”的空间。 不同文档中的范围是否矛盾。 当前资源与周期下是否可交付。 是否能判断实现是否越界。 Story / Design / Task 是否都位于范围内。
Scenario / Flow 主路径、关键分支、角色、触发条件是否缺失。 前置条件、触发、过程、结果是否清楚。 不同场景是否定义冲突。 流程在平台/系统约束下是否可落地。 每个关键路径是否有可观察结果。 是否被 Design / Task / AC 承接。
Rule 适用条件、结果、优先级、例外是否完整。 规则语义、边界、优先级是否明确。 规则之间、规则与场景之间是否冲突。 规则是否能被系统可靠执行。 规则是否有判定依据。 是否映射到实现机制和验收定义。
State / Transition 状态集合、进入/退出条件、迁移是否遗漏。 各状态含义及转移触发是否明确。 是否出现非法或矛盾迁移。 状态模型是否能由现有系统支撑。 状态变化是否可观测、可断言。 是否有对应实现与验证。
Edge / Failure 关键失败、异常、边界、恢复场景是否遗漏。 失败后的行为、提示、重试、恢复是否明确。 与正常路径、Rule、State 是否冲突。 恢复/重试/降级策略是否可实现。 是否能够模拟并验证失败结果。 是否存在对应设计、任务和验收覆盖。
Data / Business Object 字段、实体关系、生命周期、默认值是否缺失。 null、空值、单位、枚举、时间语义是否明确。 跨文档、上下游的数据定义是否一致。 现有存储/同步/迁移机制是否支持。 结果数据是否可检查、可断言。 是否映射到 API、存储、实现和验证。
API / Contract 输入、输出、错误、超时、版本等是否完整。 字段、错误码、幂等、重试语义是否明确。 提供方与消费方定义是否一致。 接口能力是否真实存在且满足要求。 是否能够验证契约行为。 是否被调用链和实现计划承接。
Dependency 外部系统、能力、人员、版本依赖是否识别。 责任边界、可用性、SLA 是否明确。 双方约定是否一致。 依赖是否已存在、可访问、可按期提供。 关键依赖条件是否可验证。 是否进入 Design / Task / Risk。
NFR / Constraint 性能、安全、可靠性、兼容性等是否遗漏。 约束是否量化或具有明确判据。 约束与功能需求、方案是否冲突。 目标是否技术可达。 是否存在验证方法和阈值。 是否进入设计、实现任务和验证。
Design 关键组件、数据流、接口、异常策略是否缺失。 组件职责、关键机制、决策边界是否明确。 是否与 Requirement / Constraint 冲突。 方案是否符合代码库、平台、架构现实。 是否说明关键设计如何被证明。 是否覆盖所有关键 Requirement。
Plan / Task 是否遗漏关键实现、迁移、配置、验证工作。 任务是否足够具体可执行。 是否与 Design、Requirement 冲突。 依赖顺序、资源和前置条件是否满足。 是否包含对应验证动作。 Requirement → Design → Task 是否闭合。
AC / Expected Result 关键行为是否都有验收定义。 正确结果是否明确、无主观词。 是否与 Rule / Scenario / Constraint 一致。 是否可以在现实环境中执行验证。 是否有客观、可观察、可判定结果。 是否覆盖关键 Requirement 与风险。

5. Finding 模型

Finding 不是新的“检查维度”，而是检查矩阵发现的问题实例。推荐统一结构：

Finding = Object × Attribute × Problem Statement × Evidence × Impact × Suggested Resolution × Status

5.1 推荐字段

字段说明示例
Object问题发生在哪个检查对象。Scenario
Attribute违反哪个质量属性。Completeness
Problem具体缺口、歧义、冲突或不可验证点。账号被冻结状态下的支付行为未定义。
Evidence能够定位问题的原文、章节、关系或代码/契约证据。Scenario-03 仅覆盖 Active Account。
Impact如果不解决，可能改变什么。支付是否允许会出现两个合理实现。
Resolution需要谁补什么信息或解决什么冲突。产品确认 Frozen Account 的支付策略。
StatusOpen / Resolved / Accepted Assumption。Open

5.2 示例

Finding A — Behavior × Completeness
账号被冻结时，支付行为未定义。当前 Scenario 仅描述 Active Account。若不补充，Agent 可以合理实现“禁止支付”或“允许现有交易完成”，会产生不同业务行为。
Finding B — API Contract × Consistency
API 文档定义 null = 不修改，业务 Rule 定义 null = 清空字段。两者不能同时成立。
Finding C — AC × Verifiability
AC 仅描述“页面应快速打开”，没有明确阈值、比较基线或其他可观察判据，因此无法形成客观验收结论。

6. BLOCK 判定

关键原则：Completeness、Clarity、Consistency 等并不天然等于 BLOCK。
Gate1 应根据 Finding 的 Materiality（实质影响） 决定是否阻断。

6.1 BLOCK 的核心判据

当一个未解决 Finding 会迫使实现者或 Coding Agent 自行做出一个会显著改变结果的决策时，应 BLOCK。

影响维度典型情况Verdict
User Behavior不同解释会导致用户看到不同流程、权限、提示、结果。BLOCK
Business Semantics会改变业务规则、金额、权限、资格、生命周期等。BLOCK
Data Semantics会改变数据含义、状态、保存/删除/同步结果。BLOCK
ArchitectureAgent 必须自行决定关键组件边界、持久化、同步、容灾等重要方案。BLOCK
Security / Privacy / Compliance可能导致权限、安全、隐私、法规结果不同。BLOCK
External Contract上下游协议、错误语义、幂等、兼容性可能出现不同实现。BLOCK
Acceptance Result无法确定完成后什么结果算正确。BLOCK
Low-risk implementation detail局部实现细节不影响外部行为和验收，可采用合理默认值并记录。WARN / ASSUMPTION
Naming / Style / Local choice变量名、局部组织、无外部影响的低风险实现选择。PASS

6.2 六类典型 BLOCK

BLOCK-1 关键定义缺失

缺失会导致用户行为、业务结果、数据、安全、接口或验收结果出现不同实现。

BLOCK-2 关键定义存在多种合理解释

Agent 无法根据现有规则安全选择，并且不同选择会改变重要结果。

BLOCK-3 关键定义互相冲突

Requirement、Rule、UX、API、Design、Task 之间存在会影响实现的冲突。

BLOCK-4 要求或方案不可成立

平台、依赖、接口、架构或性能约束使要求无法可信实现。

BLOCK-5 关键行为不可验证

无法客观定义什么结果算正确，导致实现完成后也无法判定。

BLOCK-6 关键需求在下游丢失

重要 Requirement 没有被 Design / Plan / Task 承接，或存在无来源的关键实现。

7. Gate1 判定流程

1. 建立检查对象集合 ↓ 2. 对每个重要对象执行 Object × Attribute 检查 ↓ 3. 形成 Finding，并附 Evidence ↓ 4. 判断 Finding 是否造成 Material Decision ↓ 5. 若是高影响未决决策 → BLOCK 若是低风险可默认 → WARN / Accepted Assumption 若无实质影响 → PASS ↓ 6. 所有 BLOCK Finding 关闭后，Gate1 才可 PASS

7.1 推荐的最终 Verdict 规则

PASS

不存在未关闭的 material finding；剩余项不会迫使实现者做高影响决策。

WARN

存在低风险缺口，但有安全默认值或已记录 assumption，不影响关键行为与验收。

BLOCK

至少存在 1 个未关闭的 material finding，会迫使实现者自行决定重要语义或无法形成可信验证。

8. 对 LLM Gate1 实现的直接指导

  • 不要直接问：“这个 PRD 是否可以开发？”——过于主观。
  • 先构造对象清单：Intent、Behavior、Data、Contract、Constraint、Design、Verification。
  • 再按属性审查：Completeness、Clarity、Consistency、Feasibility、Verifiability、Traceability。
  • 每个 Finding 必须带 Evidence：不能只有抽象判断。
  • 把发现问题与阻断决策分离：Finding 发现由 LLM 强语义推理完成，BLOCK 由 Materiality + Gate Policy 决定。
  • 允许低风险 Assumption：Gate1 的目标不是消灭所有未知，而是消灭未决的高影响决策。
  • 输出结构化结果：建议同时产生 HTML 给人审阅、JSON 给 CI/Agent 消费。
