01

Refinement · 需求精炼

目标：在已知业务范围内精炼 AC、推断候选前提并寻找缺失行为

官方已有
1.1 INPUT

读取 User Story / AC 与输入约束

以已给出的目标和范围为条件，检查现有需求；不在这里重新决定业务意图

→
1.2 REASON

LLM 溯因推理

从目标成功状态倒推必要前提、状态与条件

→
1.3 DISCOVER

挑战前提及异常路径

若条件不满足会怎样？是否已有 AC 覆盖？

↓
1.4 CHECK

改进已有 AC

EARS 模式、模糊量词、实现语言、可观察输入输出

→
1.5 OUTPUT · ①

修订 AC + 待确认候选 AC

改进表达、发现缺口；新增规则在确认前不得直接变成正式需求

输出：Refined EARS AC + 待确认候选 AC → Stage 2

需要增强的位置

↳输入契约 · 不是内部增强点

业务目标、范围和已确认约束来自上游。Kiro 分析中可检查 AC 是否偏离这些输入，但不承担业务目标的发现、评估和范围决策。

处理规则：可引用、可质疑、可发起澄清；不可凭推测擅自改写业务边界。
①P1候选 AC 的来源与确认机制

溯因推理能发现遗漏，但也可能引入未经业务授权的规则，导致需求范围被隐性扩展。

增强方案标记 Proposed / Confirmed，保存候选 AC 的推断依据、来源和影响范围；待业务确认后再写入正式规格。
↓
02

Auto-formalization · 自动形式化

目标：构造 SMT-LIB 逻辑模型，并主动发现语义歧义

官方已有
2.1 SCHEMA

定义符号与实体关系

Entity / State / Event / Input / Output；符号附自然语言描述

2.2 ASSERTIONS

AC 转换为逻辑蕴含

Guard → Response；将 EARS 转为形式化约束

2.3 BACKGROUND · ②

生成背景断言

LLM 多次抽样隐含领域知识，按照出现频率筛选

↓
2.4 SAMPLE

多次独立形式化

同一 AC 生成多个候选逻辑解释

→
2.5 CLUSTER · ③

SMT 逻辑等价聚类

对不同候选按语义等价分类，计算 Semantic Entropy

2.6 语义熵分支（双阈值 low / high）

低熵：接受

选多数语义簇的代表形式化模型 → 进入逻辑分析

中熵：澄清

Semantic Diff → 找差异情境 → 用户选择解释 → 修订模型/需求

高熵：弃用

形式化不稳定 → 不采用本次结果 → 要求重新表述 EARS

输出：Schema + AC Assertions + Background Assertions → Stage 3

需要增强的位置

②P0 · 最高优先可信领域知识建模

官方明确指出：LLM 生成并按频次筛选背景知识仍可能遗漏关键领域约束，导致不现实的反例、虚假冲突与错误完整性判断。

增强方案以有出处的领域知识包替代纯抽样依赖；引入事实、Rule、State Transition、Invariant、适用范围及可信状态。
③P1形式化可信度校验

“多次翻译一致”只能说明 LLM 输出稳定，不等于需求语义正确。

增强方案校验符号覆盖、类型、来源映射及差异反例；对关键 AC 强制用户审查，不以低熵替代真值证据。
↓
03

Logical Analysis · 逻辑分析

目标：利用 SMT 求解器探索约束冲突、规则空白、允许和禁止的行为

官方已有
3.1 CONSISTENCY

冲突检测

触发条件同时成立时，输出约束是否互斥；定位最小冲突规则组

3.2 COMPLETENESS · ④

完整性检测

搜索没有具体规则覆盖的状态/条件组合

3.3 SCENARIO · ④

行为情境探索

采样 Accepted Scenario 与 Rejected Scenario

↓
3.4 LLM JUDGE

基于 User Story 过滤“令人意外”的行为场景

减少向用户展示的场景数量；它是问题筛选器，不是正确性证明

↓
3.5 FINDINGS

生成五类澄清问题

AmbiguityConflictCompletenessAccepted ScenarioRejected Scenario
输出：具体情境 + 涉及的规则 + 解释 + A/B 修订选项

需要增强的位置

④P1时序、状态与风险场景增强

一次性输入状态的组合检查无法天然保证真实跨事件流程、并发与重试行为都被充分探索。

增强方案增加可达性模型、Transition、Bounded Temporal Properties、Invariant，以及历史缺陷风险模式；用风险排序与覆盖指标辅助 LLM Judge。
↓

4.1 REWRITE · ⑤

LLM 根据确认结果修订 requirements.md

更新受影响的 EARS AC；用户可在修改后再次 Analyze Requirements，对相关要求及其相互作用重新检查

输出：更新后的需求规格 → 设计阶段；也可再次分析 ↺

需要增强的位置

⑤P0证据链、重分析与验证契约

官方重点展示的是修改规格与生成澄清问题，文章未充分说明企业级版本化证据、回归判定及验证资产交接。

增强方案保存 原始文本 → IR → SMT 查询 → 模型/反例 → 澄清选择 → 新 AC 的关系；输出 Oracle、Invariant、Test Obligation，并对未闭环的高风险问题阻断。
↓

五项内部增强点 · 优先级速查

序号优先级位置建议新增能力核心收益
①P1Stage 1 输出候选 AC 溯源、确认与范围控制防止 AI 补全直接变成未授权业务规则
②P0Stage 2 · Background可信领域知识包 / 规则 / 状态 / 不变量减少不真实反例，提高逻辑结论可靠性
③P1Stage 2 · Formalization形式化忠实度与语义映射校验避免“低语义熵 = 正确”这一误判
④P1Stage 3 · Analysis可达状态、时序、并发、风险场景探索提升跨事件与高风险缺陷的发现能力
⑤P0澄清修订 / 输出证据链、重验证、Oracle / Test Obligation将需求分析成果持续传递给设计与验证
范围调整说明：原增强点“输入：意图与范围证据”已移出内部增强列表，改为上游输入契约。它不是“不要检查意图与范围”：当上游提供可信约束时，分析仍可识别需求与既定边界的不一致；但业务意图的创建、论证和最终决策不属于本流程。
