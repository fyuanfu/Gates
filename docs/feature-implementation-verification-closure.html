Feature 实现与验证闭环流程

把 Feature 从声明意图推进到可执行实现，再通过两条独立但互补的证据路径完成准出：Converge 负责验证实现与意图的一致性，Verification 负责验证运行行为是否满足测试 Oracle，最后统一形成 Evidence 与 Verdict。

Intent → FR / AC / Rules → Plan → Tasks → Implementation → { Converge + Verification } → Evidence → Verdict

1. 整体流程总览

主链路先完成意图下沉和实现；实现完成后分成两条证明路径，最后在证据层汇合。

2. 这条闭环真正要证明什么

意图完整下沉

每一个重要 FR / AC / Rule 都必须在 Plan、Tasks 和 Implementation 中找到承接关系，避免需求存在但没人实现。

实现忠实

Converge 负责判断代码有没有完整兑现已经声明的意图，重点是完整性、一致性和实现漂移。

行为正确

Verification 负责通过测试执行 + Oracle 判断系统运行起来以后是否真的正确，避免只靠静态代码推断。

①

Intent → FR / AC / Rules：把目标变成可判断的需求义务

这是整个闭环的起点。后面所有 Plan、Tasks、Evidence 都必须能追溯回这里。

输入

  • Feature 目标 / 用户问题
  • 产品范围与非目标
  • 用户旅程 / 场景
  • 外部系统与平台约束

处理

  • FR：系统必须提供的能力。
  • AC：用户或业务如何判断该能力被接受。
  • Rules：状态、边界、约束、优先级、不变量。
  • 将模糊目标转换为可判定描述，必要时补充 Scenario / State / Data。

产物

Intent Inventory
├─ FR-001
├─ AC-001
├─ RULE-001
└─ ...
门槛：如果某条需求无法回答什么情况下算满足 / 不满足，它还没有准备好进入后面的工程实现链。
②

FR / AC / Rules → Plan：把业务义务分配成技术责任

Plan 的作用不是重复需求，而是回答由谁、在哪里、用什么机制实现。

分配对象

  • 模块 / Component
  • 接口 / API
  • 数据模型 / 持久化
  • 状态机 / 调度 / 并发
  • 平台能力 / 外部依赖

核心处理

  • 把 FR 分配给负责组件。
  • 把 AC 转成需要被支持的行为路径。
  • 把 Rules 转成状态、校验、约束或恢复策略。
  • 定义跨模块接口、数据契约和异常责任。
  • 识别必须通过测试证明的风险点和 Oracle 候选。

典型输出

FR-008
→ UploadWorker
→ UploadRepository
→ PendingUploadEntity
→ NetworkConstraint
→ Retry Strategy
③

Plan → Tasks：把技术责任拆成可执行、可验证的工作单元

Task 不是简单 TODO，而是 Plan 与 Implementation 之间的工程桥梁。

Task 必须包含

  • 明确动作
  • 对应模块 / 文件
  • Source Ref：FR / AC / Rule / Plan
  • 完成条件
  • 必要的测试工作

拆解原则

  • 一个 Task 应能独立执行并判断完成。
  • 实现任务和验证任务要分离。
  • 关键 Rule 必须有对应实现任务。
  • 不可把多个高风险行为塞进一个大任务。

示例

T021 实现 PendingUpload 持久化
Source: FR-008 / RULE-04

T022 实现网络恢复调度
Source: AC-03 / PLAN-07
④

Tasks → Implementation：执行实现，并留下可追溯结构

这里产出的不仅是代码，还包括后续两条验证路径所需要的结构和资产。

实现资产

  • 业务代码
  • 数据结构
  • 配置 / Feature Flag
  • 接口实现
  • 异常与恢复路径

可追溯资产

  • 变更文件 / Component
  • Task → Code 映射
  • Commit / Diff
  • Requirement → Implementation 锚点

验证资产

  • Unit / Integration / UI tests
  • Test data
  • Mock / Fake / Harness
  • 运行环境与日志能力

3. 实现完成后分成两条证明路径

这两条路径不能互相替代：Converge 偏实现一致性证明，Verification 偏运行时行为证明。

路径 A：Converge

建立 Intent Inventory → 映射 Code Scope → 查找实现证据 → Expected vs Actual → Missing / Partial / Contradicts / Unrequested → Finding → 修复任务 → 再次收敛。

路径 B：Verification

Verification Objective → Oracle → Test Condition → Test Case → Execution → Actual vs Expected → Pass / Fail / Inconclusive。

核心区别：Converge 证明实现是否忠实；Verification 证明系统真实执行行为是否正确。

4. 路径 A：Converge — 实现忠实度闭环

输入基准

  • FR / AC / Rules
  • Plan 决策
  • Tasks
  • Constitution / 工程约束

核心算法

  • 建立 Intent Inventory
  • Intent → Code Scope
  • 查找实现证据和反证
  • Expected vs Actual 语义比较
  • Gap 分类与严重度判断

Gap 类型

  • Missing：没实现
  • Partial：部分实现
  • Contradicts：实现冲突
  • Unrequested：多做未声明行为
Converge 回答：我们已经承诺实现的东西，在代码里是否完整、一致地兑现了？它不等同于运行测试成功。

5. 路径 B：Verification — 运行时行为证明

阶段核心问题主要输入输出
Verification Objective这条需求需要证明什么？FR / AC / Rules / Risk验证目标
Oracle怎样判断结果正确？规则、状态、契约、期望结果判定标准
Test Condition哪些条件组合必须被验证？Scenario / State / Rule / Data / Failure Mode测试条件
Test Case如何在具体环境执行？Test Condition + 架构 + 测试资产可执行测试
Execution系统真实行为是什么？代码 + 环境 + 输入日志、结果、截图、Trace
Oracle CompareActual 是否等于 Expected？运行结果 + OraclePass / Fail / Inconclusive
关键：Verification 不是看代码应该能工作，而是执行真实条件，并用 Oracle 对实际结果做判定。

6. Evidence：两条路径如何汇聚

实现证据

  • FR / AC / Rule → Code 映射
  • 关键类 / 方法 / 状态机 / 数据契约
  • Converge Finding 及关闭记录
  • Task / Diff / Commit Traceability

运行时证据

  • Test Case 执行结果
  • 日志 / Trace / Screenshot / Report
  • 设备、系统、网络、账号等环境信息
  • Oracle 判定与失败证据
Evidence 不是测试通过截图集合：它必须能够反向回答这个 Verdict 基于哪条 Intent、哪种验证义务、哪些具体证据得出。

7. Verdict：最终准出判定

判定维度PASS 条件阻断示例
需求实现完整性关键 FR / AC / Rule 均有实现证据BLOCK 核心 FR Missing
实现一致性无未关闭的核心 Contradiction / PartialBLOCK Rule 与代码行为冲突
行为正确性关键 Verification Objective 均有 Pass 证据BLOCK P1 场景测试失败
Oracle 完整性所有关键 AC / Rule 均有明确判定标准HOLD 无法判断 Expected Result
证据可追溯性Intent → Plan → Task → Code → Test → Evidence 可追溯HOLD 有结果但无法确认覆盖哪个 Requirement
遗留风险无未接受的 Critical / High 风险BLOCK 高风险问题无 owner / 无处置

8. 完整闭环状态

意图已定义 → 方案已分配 → Tasks 已执行 → 实现完成 → {Converge 无阻断 + Verification 关键目标通过} → Evidence Complete → Verdict PASS
失败回路：Converge 发现 Gap 时转成 Traceable Task 返回 Implementation；Verification 失败时形成 Defect / Finding，修复后必须重跑相关测试与受影响范围。

9. 示例：相册上传过程网络中断

层次示例内容
Intent用户上传照片时，即使出现短时网络中断，也不应丢失上传任务。
FRFR-008：网络恢复后，未完成上传任务应自动继续。
ACAC-03：上传到 40% 时断网，恢复网络后无需用户重新选择照片，任务继续并最终完成。
RuleRULE-04：同一任务不得因恢复网络创建重复记录；RULE-05：超过最大重试窗口后进入可恢复失败态。
PlanWorkManager + 网络约束 + PendingUpload 持久化 + 唯一任务键 + retry/backoff。
TasksT021 持久化 PendingUpload；T022 网络恢复调度；T023 唯一任务去重；T024 测试断网恢复。
ImplementationUploadWorker、UploadRepository、PendingUploadEntity、UploadScheduler、测试代码。
Converge发现有 retry 但进程被杀后状态丢失 → Partial / HIGH，补充持久化与恢复任务。
Verification执行上传 40% → 断网 → 杀进程 → 恢复网络 → 重启；Oracle：恢复同一任务且无重复记录。
Evidence代码映射 + Finding 关闭记录 + 测试日志 + DB 状态 + WorkManager Trace + 最终结果。
VerdictConverge 高风险 Finding 全部关闭且关键断网恢复测试通过，才允许 PASS。

10. 最重要的职责边界

Converge

证明实现忠实。
回答声明的东西有没有实现完整、有没有冲突、有没有实现漂移。

Verification

证明行为正确。
回答真实测试条件下 Actual 是否满足预先定义的 Oracle。

Verdict

证明可以准出。
要求两类证据共同成立，而不是只看代码检查或只看测试通过率。

一句话总结：Converge 解决有没有把该做的做完整，Verification 解决做出来的东西运行起来对不对，Evidence 把两种证明组织起来，Verdict 才能做真正的 Feature 准出判断。
