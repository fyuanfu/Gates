本报告的核心观点

Anthropic 已经提出系统化的 Agent 执行与治理框架；要构建面向复杂业务的软件质量保证体系，仍需补充独立的规格质量判断、可追溯的测试义务及风险驱动验证。

阅读标识

原文事实配有 [S1]–[S6] 来源；分析判断 / 需要补充 / 建议是本报告的独立延伸，不能与官方实践混同。

01 核心理念

从“编码加速”走向“交付系统重构”

Anthropic 的判断不是“AI 代替写代码”这么简单，而是：当编码速度显著提升，原本依靠人工交接、等待和审批的流程会成为新的系统瓶颈。真正的转型对象是整个 SDLC。

“
Code is no longer the bottleneck.

这是一项关于系统约束迁移的判断，而不是“代码质量已被 AI 自动解决”的证明。[S1]

1.1 传统流程为什么会受到冲击

传统 SDLC 围绕高成本的人类编码活动设计：产品写 PRD，技术架构师负责设计，开发实现，QA 验收，发布团队把关。角色边界与阶段交接确保责任可追踪，但也引入等待时间。当实现周期明显缩短后，这些静态环节的吞吐量不再匹配代码产出速度。

瓶颈转移

Plan / Test / Deploy

需求明确、评审、验证、发布审批成为新的排队点。

控制失配

Review 不可线性扩容

逐行人工审查无法随 Agent 产出数量无限同比扩张。

治理滞后

审批仍以会议为单位

例外处置与决策时延抵消代码生成带来的收益。

1.2 “AI-Native”的五个核心变化

维度传统 SDLCAI-Native SDLC必须保留的控制目标
入口多次沟通形成需求文档自然语言意图沉淀为版本化 intent.md问题与目标被真实理解
设计分析、设计分阶段交接Agent 结合组织标准生成 spec.md规格正确、设计风险透明
实现代码与测试以人工为主Plan-first，Agent 执行并自验证关键技术决策可审查
验收阶段结束后集中验证运行中的反馈循环与配置 Evals结果有客观证据
治理人工审查、会议式审批策略、Hooks、分级人工批准高风险决策仍有责任人
维护人发现、诊断、提单指标触发 Agent 诊断，重启意图闭环线上变化可控、可回溯
分析判断

速度增加不自动提高质量。必须同步提高需求可验证性、变更风险识别能力、验证吞吐量和治理确定性；否则只是把瓶颈从编码团队搬到代码评审或测试验收团队。

1.3 适用范围与边界

原文主要面向已经采用 Claude Code、具备 Git 与 CI 基础设施、能够调整审批和发布流程的工程、平台与安全负责人，尤其考虑大型或受监管组织。文中的做法是 可按依赖逐步采纳的 Plays，并不是所有企业必须一夜之间照搬的统一强制流程。[S3]

02 总体架构

六阶段、12 项 Plays 与 Artifact-driven Workflow

保持 Plan、Design、Build、Test、Deploy、Maintain 六个控制目标，但把阶段间的“人传话”替换为“可读取、可审批、可触发的交付件”。

02Designspec.md行为与设计
→
03Buildplan.md / diff方案与实现
→
04Testtest evidence持续验证
→
05DeployPR / release审批与发布
→
06Maintainincident指标与反馈
↩ 运行事件、事故与改进建议重新形成 intent.md，返回 Plan

分析报告重绘示意：简化了阶段并行与条件分支，不意味着 SDLC 必须严格线性执行。

2.1 核心交付件和审计链

→

→
plan.md如何实现
→
Code + Tests实现与证据
→

交付件链既是上下文传递机制，也是责任与审计线索：谁提出需求、Agent 产生了什么、由谁批准、代码和测试是否与计划一致。原文建议每个阶段提交可追踪资产，重要审批通过 Merge 或 Review 记录完成。[S1]

2.3 两条基础原则

权威数据源（Source of Truth）

若需求仍以 Jira / ServiceNow 等为权威系统，Markdown 可是工作副本；如果 Git 为事实来源，传统平台保存指向提交的链接。至少应有记录 ID 与 Commit SHA 的双向关联，避免双写漂移。

依赖优先于阶段顺序

原文有依赖图，允许按团队瓶颈从基础能力切入：例如先具备可运行测试，再构建 Evals；先有 PR 评审与审批控制，再让 Agent 介入 CI/CD 中的写操作。

架构要点

可验证交付链不是“所有内容统一放 Markdown”，而是每种资产有权威来源、稳定标识、状态、责任人、上下游引用与批准证据。这决定了 Agent 工作流是否具有可审计性。

03 逐阶段机制

六阶段怎么运行：输入、动作、出口与风险

以下按官方工作方法逐一解读，并在每一阶段单独标明质量工程视角下需要加强的地方。所有扩展建议都不代表官方已经落实。

01
PLAN

捕获意图，而不是一开始就写完整 PRD

业务发起人描述真实问题，Claude 以追问方式整理影响对象、目标结果、约束、非目标与开放问题，形成 intent.md；发起人校正，产品负责人接受或拒绝，随后进入规格生成。人工责任不被取消。[S1]

输入业务痛点 / 工单 / 事故 / 访谈
主要输出intent.md
决策人发起人与 Product Owner
官方关注的指标意图提交耗时、通过率、后续改写率
# Intent: 导入操作的异常恢复
## Problem
应用进程被终止后，失效的运行记录可能阻止用户再次导入。
## Outcome
用户可重新发起合法导入，且不会产生重复执行。
## Constraints
持久化数据兼容；不得删除用户导入数据。
## Open Questions
怎样判定“失效任务”？重启时是否尝试继续执行？

需要补充：intent.md 解决意图保真，不自动保证需求完整。完整性判断必须在后续阶段对业务对象、状态与异常组合进行系统检查。

02
DESIGN

把需求规格生成与组织标准约束放到同一工作过程

批准 intent.md 后，Agent 加载组织的安全、合规、UX、品牌规范及相关工程上下文，生成 spec.md，列出无法满足或彼此矛盾的政策、未决风险。Product Owner 审查“设计是否解决了原始问题”，高风险事项升级到技术负责人。[S1]

输入intent + 标准 Skills + 既有系统知识
输出spec.md + flagged concerns
决策人产品负责人；必要时技术负责人
官方关注的指标意图到规格的耗时、开发后规格返工

需要补充：建议把 Story → AC → Scenario / State / Rule / Invariant 作为需求质量约束，不允许“未确认的关键业务假设”以已批准规则的形式混入规格。

03
BUILD

Plan-first：在修改代码前暴露关键实现决策

工程师以 Plan Mode 阅读已批准规格和现有代码，Agent 给出涉及文件、实施顺序、风险、替代方案、测试证明。反复审查直到一位未参与会话的工程师也能依照计划实现；随后批准 plan.md，执行代码修改。若实现偏离计划，必须同步修订。[S1]

输入spec、代码仓、工程知识
输出plan.md + code diff + tests
决策人工程师；高风险由架构负责人
官方关注的指标首轮合并率、返工次数、Plan-Diff 一致率

原文还鼓励基于 Git worktree 的并行 Session，以及使用受限工具与独立上下文的 Subagent 执行专项工作。其收益取决于任务是否真正可分割，而非同时启动的 Agent 数量。

需要补充：计划应该解释“为何影响这些 Feature / Scenario”，而不止罗列文件。对于 Brownfield 工程，需加入跨模块影响范围和变更风险来源。

04
TEST

开发内反馈闭环 + Agent 配置回归，两套验证体系并行

官方要求把 Build、Unit Test、Lint、视觉截图等做成 Agent 可直接调用且有可判断退出码的能力，禁止“没有运行工具却宣布已完成”。修复缺陷时先有失败测试、确认失败原因，再修改实现，并防止 Agent 通过改弱测试造假。[S1]

生成 / 修改实现
→
真实执行 Test / Build
→
失败归因与修复
↺
验证日志 + 证据

Feedback Loop 贯穿单项任务；Verifier Subagent 使用新上下文进行最终检查，两者不是同义词。

与此同时，Agent Evals 针对 CLAUDE.md、Skill、Hook、Prompt、模型变化做能力回归。原文建议先收集 20–50 个真实任务，并配置被接受的结果和检查器；可在配置变更、定时调度或事故发生后追加执行。[S1]

软件测试代码行为与系统需求是否符合
Agent EvalsAgent 是否仍按预期完成工作
证据要求真实工具日志、退出码、工件、截图
官方关注的指标首次 CI 通过率、Eval 通过率、生产回归

需要补充：“测试通过”仍然依赖测试是否覆盖正确业务要求，须区分 AC、Test Obligation、Oracle 和真实执行结果；配置 Evals 也不能替代设备级软件验证。

05
DEPLOY

Agent 审查所有 PR，但关键审批依旧由受权人员负责

原文将 PR 审查拆成 Bugs、Security、Compliance 等 Pass，并以 REVIEW.md 指定严重程度、排除规则与规范引用；审查结果可供 CI 决策，但不能直接取代 Code Owner 的审批。Agent 可以跟进修复 Reviewer Comment，但必须经过保护分支与审查路径。[S1]

部署自动化按权限分层：先让 Agent 只读定位失败、生成变更日志；再允许其在受控流水线中提交修复 PR；更高自主级别必须满足隔离沙箱、短期权限凭证、明确的部署 MCP 工具范围和已演练的回滚路径。生产发布需要人授权。

输入Code Diff + Plan + Spec + Policy
输出Findings、批准记录、部署状态
审批位置Code Owner / Release Manager
官方关注的指标审查质量、PR 等待时长、发布失败与恢复

需要补充：不能让模型对每个动作的自由裁量取代访问控制；Hooks 只对受控工具路径有效，还需 CI 权限、网络隔离与审计记录。

06
MAINTAIN

确定性检测异常，Agent 诊断，再生成下一轮意图

监控脚本根据统计控制带检测异常：如 CI 失败率、发布后 5xx 比例。1σ 记录、2σ 只读诊断、3σ 提议 PR 或触发预授权回滚 Runbook。Agent 将证据与建议写成新的 intent.md，值班人员决定修复、延期或忽略；事故转化为回归用例。示例控制带不是通用可靠性标准。[S1]

输入监控指标、日志、事故信号
输出诊断 + intent + 事故记录
决策人Service Owner / On-call
官方关注的指标检测至入队耗时、转修复率、同类问题复发

需要补充：生产自动化必须区分观测、诊断、可逆处置与有破坏性的操作；不要把示例的 1σ/2σ/3σ 直接作为业务告警生产阈值。

04 工程化机制

CLAUDE.md、Skills、Hooks、Evals 到底如何分工

这些工具都承载知识或规则，但处于不同控制层。如果将所有要求写在一个长 Prompt 中，会把组织制度误当成模型应当“记住”的自然语言建议。

机制责任执行特性资产例子关键边界
CLAUDE.md项目环境与惯例会话上下文常用命令、架构、易犯错误不是强制安全隔离
Skill可复用工作方法与组织知识模型理解后应用安全 API 检查 Skill具有建议性质，需验证是否触发
Hook工具调用边界控制匹配事件时执行代码禁止修改保护目录依赖受控配置与运行环境
REVIEW.mdPR 多维评审准则审查配置 / 规则Bugs / Security / Compliance发现本身不代表合并获批准
EvalsAgent 工作能力回归任务 + 判分检查模型变更后安全任务表现不等同于软件业务验收
CI / Sandbox确定性验证、权限与隔离系统层强制测试门禁、短期凭证需独立于模型的权限边界

4.1 CLAUDE.md：紧凑、更新频繁、对整个团队一致

原文建议由仓库初始化生成起点，再压缩到新同事第一天真正需要了解的内容：Build/Test/Lint 命令、技术约定、关键架构、反复出现的错误。典型准则是 Agent 连续两次犯同一类错误，就将改正信息沉淀至 CLAUDE.md。文件应足够精简，并通过 PR 管理。[S1]

# Gallery module
## Commands
- Build: ./gradlew :gallery:assembleDebug
- Unit test: ./gradlew :gallery:testDebugUnitTest
- Lint: ./gradlew :gallery:lintDebug
## Invariants / conventions
- Do not edit generated sources.
- Account-scoped operations must preserve account identity.
## Common mistakes
- A persisted RUNNING flag is not proof that work is alive.

4.2 Skills：把重复依赖个人经验的活动产品化

Skill 有明确触发描述、操作步骤、可调用脚本、可能还有模板和检查项。适合持续复用的安全标准、代码 Review、需求挑战、变更影响分析等。Skill 的触发和有效执行要通过真实任务验证。当政策必须无例外执行，应在 Hook 或 CI 再加确定性检查。[S1]

4.3 Hooks：程序性强制控制，不能混淆“建议”与“强制”

例如某个文件编辑操作发生前，在 PreToolUse Hook 检查路径是否受保护，不合规就返回阻断。对于更复杂的发布操作，应该在外部审批系统验证身份与授权，而不是仅判断命令中包含 production 字符串。

关键安全提醒

官方展示的 Bash 字符串匹配脚本是说明控制思路的简化例子，不能单独当作生产环境安全边界。正确的保护应采用受管理的权限配置、OS/容器隔离、网络白名单、CI 权限及发布系统自身的授权。

4.4 Evals：测试的是工作代理，而不仅是产品代码

每个 Eval Case 最少包括任务输入、预期/允许行为、执行环境、判分器和失败证据。配置变更后跑回归；生产事故转化为样本；通过率下降阻止相关配置合并。建议记录模型版本、Skill 版本、运行预算、判分器版本，以免“前后对比”缺少实验可重复性。

{
  "eval_id": "API-AUTH-007",
  "task": "为既有服务新增查询接口",
  "expected_checks": [
    "新增接口具有鉴权机制",
    "集成测试包含未授权访问拒绝",
    "修改没有扩大敏感数据暴露面"
  ],
  "grader": "unit-tests + policy-check + review"
}

上例是本报告为解释 Eval 结构编写的示意，不是 Anthropic 原文所提供的正式 Schema。

4.5 单一大 Agent 与多 Agent 的取舍

独立 Reviewer 或 Subagent 的意义在于限定职责、减少无关上下文干扰、增加独立判断机会。但它们仍可能共享同一份不完整需求、知识库偏差或错误的验证目标。工程设计上应优先明确工作契约、信息来源和评审界限，其次才是增加 Agent 数量。

05 独立分析 / 质量视角

Playbook 解决了什么，又没有解决什么？

这份文档是一套成熟度较高的 Agent 研发工作流与治理指导，但并非完整的软件正确性证明方法。它系统解决了流程交接、策略嵌入和验证反馈，却没有在同等深度上形式化定义业务规格的充分性。

判定边界

以下五项是本报告基于质量工程的分析和建议；“官方未系统展开”不等于 Anthropic 内部完全没有相关能力，更不能据此断言相关能力不存在。

5.1 需求完整性：存在“正确执行错误规格”的风险

官方已解决：意图生成、组织政策约束、规格问题上报、产品负责人审批。

仍需补齐：针对业务对象、事件、状态、规则、数据边界、跨功能依赖和非功能约束的系统性缺失检测。仅让 Agent 生成完整 spec.md，没有等价于它已识别所有隐藏的业务前提。

待检查维度典型缺口建议方法
对象未定义 ImportTask 与 Work 实例是否为同一对象实体/关系模型、术语表、本体
状态遗漏进程死亡后 RUNNING 的合法性状态机、转移表、反例搜索
规则“有运行记录”被误当作“有活跃工作”业务不变量与决策表
场景账号切换、网络恢复、重复触发未覆盖对象 × 事件 × 环境组合
一致性不同 AC 对恢复操作给出冲突结果规则对齐、SMT / 约束检查
可验证性“自动恢复正常”缺少成功判据AC → Obligation → Oracle

5.2 Verification Oracle：有工具反馈，不等于有可信判据

Anthropic 强调真实执行与受保护的失败测试，这是工程上很有价值的进步。但“测试符合写下来的预期”与“预期符合真实业务约束”不是一回事。Oracle 是用于判定某一观察结果是否正确的规则、关系或机制；测试脚本的断言只是 Oracle 的一种编码载体。

需求层Business Rule / Invariant经确认的业务事实
↓
验收层AC / Scenario可接受行为与上下文
↓
验证设计层Test Obligation必须证明的性质 + 条件 + 适用层级
↓
执行规范层Test Case + Oracle输入步骤 / 环境 / 观察点 / 判据
↓
证据层Execution Evidence日志 / 实测状态 / Trace / CI 结果

本报告提出的推荐验证资产关系，并非 Playbook 中的原生交付链。

AC、Obligation、Oracle、Expected Result 的准确关系

概念回答什么例子：导入任务
Acceptance Criteria（AC）业务在什么条件下接受系统行为？进程重启后，不存在实际活跃导入任务时，应允许发起导入
Test Obligation我们有义务验证哪些性质、边界与失败情形？验证“失效 RUNNING 记录不能阻塞新任务”，且“有效任务不能并行重复执行”
Test Oracle怎样判定观察到的系统行为正确？检查工作任务状态、返回结果及持久化记录的一致性
Test Case / Procedure怎样布置前提、执行操作、收集观察？制造旧 RUNNING 记录→模拟进程终止→重启→点击导入→检查调度状态
Expected Result在特定用例的观察点，预期出现什么？新任务成功入队且同一逻辑导入仅一个有效执行实例

这里的 Test Obligation 通常应该至少表达：验证对象、前置状态、事件或触发、必须保持的性质、反例/边界、可观察证据及适合的测试层级。Oracle 可以复用于多个用例；一个 AC 也可能拆出多个 Obligation，而一个 Obligation 可能需要多个用例或测试手段完成。

5.3 变更影响分析：从文件级计划走向业务风险传播

官方 plan.md 建议列出修改文件、步骤、风险与 Proof，属于良好的设计前评审，但不足以保证全部跨模块影响都被识别。建议补充以下可追溯路径：

Code Diff
→
影响锚点
→
功能 / 状态 / 接口
→
Risk Pattern
→
受影响 Scenario
→
Test Obligation
→
测试选择 + 缺口

从静态依赖、调用关系、数据流和显式业务映射推导候选影响，必要时保留未知风险；不应声称代码图谱本身即可发现全部业务影响。

注意要区分“已有测试能否召回”和“所需测试是否存在”。如果仅选择已有回归集，可能漏掉新增风险。应将 Test Gap 作为独立阻断或需要人工接受的风险。

5.4 自验证与独立验证：增加 Agent 不等于获得独立真相

独立 Verifier Subagent 可以降低开发过程上下文带来的偏差，却不能消除共同依赖错误规格的问题。建议至少做四层独立性设计：

  1. 上下文独立：Verifier 不只读取开发者的自我总结，直接审视批准资产与代码。
  2. 标准来源独立：AC、业务规则与不变量来自确认的需求，不由实现代码倒推生成。
  3. 执行工具独立：结论依赖真实工具/设备的返回状态，而非自述。
  4. 批准权限独立：代码产出 Agent 不拥有自我批准高风险合并和发布的权限。

5.5 质量模型覆盖：把“能运行测试”升级为“足够的证据组合”

验证层适合回答的问题高价值证据
静态规则 / 合同检查是否违反结构、接口与确定性规则？Lint、契约差异报告、Policy Check
Unit Test单一模块的业务决策是否符合规则？状态转移与边界分支测试
Integration Test数据库、WorkManager、网络依赖是否协调？组件真实联动日志
Scenario / Device Test重启、网络切换、账号变化等端到端结果是否正确？设备日志、状态快照、视频
Release / Production性能、容量、灰度、回滚是否安全？线上指标、回滚演练结果
红军审查结论

Playbook 的“反馈循环 + Evals + 治理门禁”建立了优秀的执行可靠性框架，但如果希望建立面向复杂业务的软件质量保证体系，还需要补充规格充分性检查、可追溯的测试义务、可信 Oracle、影响分析与分层证据覆盖。

06 实践证据

从 Playbook 的方法论到 Anthropic 实际运行的安全控制

同一家公司 2026 年 7 月发表的安全工程文章，为这些理念提供了真实组织实施证据。应把“官方自述的事实与指标”与“这些指标能够证明什么”分开理解。

≈80%已合并代码由 Claude 编写2026 年 7 月文章中的 Anthropic 自述
8×人均每季度代码产出文中称对比 2021–2025 时期
16% → 54%获得实质性审查评论的 PR 比例随 Agent 审查与有效性证据改进后的变化

以上仅为来源 [S2] 中的自述指标，不代表所有企业可以复制，也不能直接推导生产缺陷下降比例。[S2]

6.1 他们如何把安全左移

Anthropic 使用项目安全评审（PSR）自动化，对项目设计结合 MITRE ATT&CK 进行风险识别，并接入组织内部知识索引，获取既往政策、决策和关联系统上下文。低风险事项在信任成熟后可采用更高程度的自治，高风险依旧升级处理。[S2]

在编码阶段，安全规范写入 CLAUDE.md 与组织 Skills，并把发现的重复漏洞类型沉淀回源头；在 PR 阶段运行若干小范围 Reviewer，使用检索增强获得历史事故上下文，而不是只写一个覆盖所有漏洞类型的大 Prompt。

6.2 多重防线，而非单点“AI 审核通过”

控制层内部实践所体现的原则价值
知识侧内部知识索引 + CLAUDE.md / Skills将过去事故与既有政策带入新任务
生成侧安全代码规范在开发时介入尽可能在缺陷生成前避免其出现
审查侧多 Agent 分工审查 + 确定性检查提高覆盖面，交叉检查重要问题
权限侧身份隔离、最小权限与硬边界限制遭提示注入或越权后的损害面
治理侧Shadow Mode、人工抽样、风险分级建立可信度而不是盲目放权
监控侧代理行为与审查证据写入日志 / SIEM行为可归因、可调查

6.3 三条避免误读的结论

  1. 代码占比 ≠ 质量水平。“80% 代码由 AI 编写”描述生产方式，不能直接证明工程结果更可靠。
  2. 评论比例上升 ≠ 漏检率下降了相同比例。审查评论变多意味着系统产生更多实质性反馈，但仍需要观察误报、严重漏洞漏检和发布后事故。
  3. 自动批准需要被治理。Shadow Mode、风险分层、抽样审计和日志追踪非常重要，任何单一 Reviewer 不应成为未经验证的唯一信任来源。
实证价值判断

Anthropic 内部实践最值得借鉴的，不是某个自述产出倍数，而是从“审查代码”转向“审查 Agent 执行循环、权限、指标和决策证据”的安全与治理体系。

7.1 完整例子：导入任务因失效 RUNNING 状态而永久阻塞

缺陷场景：在应用导入过程中杀死进程，持久化的导入记录仍显示 RUNNING。再次进入 App 后，发起导入逻辑仅检查该状态，于是拒绝新导入；但真实的执行任务已不存在。注意 Android 场景下“卸载后持久化状态是否保留”受具体存储/备份机制影响，案例以进程被终止并重启、记录仍存在为清晰的可复现前提。

关键业务不变量（示意）

同一导入作用域内同时不得有两个实际有效执行的导入任务；同时，不存在实际有效任务时，旧的失效运行标记不得永久阻止合法导入请求。

从需求到可执行证据

资产示例内容谁批准 / 检查
Intent恢复用户在进程重启后的导入可用性，不产生重复执行产品负责人
AC-01无有效运行任务且仅有旧 RUNNING 记录时，允许新导入产品负责人
AC-02存在有效运行任务时，重复导入不得创建第二个有效实例产品负责人
Design Decision用可靠任务实例与持久化状态一致性作为判定基础，明确清理/恢复规则技术负责人
OB-01验证“失效记录不能阻塞合法重新发起”，包括进程终止场景质量策略 / Test Agent
OB-02验证“有效任务必须防重复”，包括高频连点及并发事件质量策略 / Test Agent
EvidenceWork 实例实际状态 + DB 快照 + API 结果 + 设备执行日志CI / Verifier / 责任人

可落地的结构化 Test Obligation（示意，不是官方 Schema）

obligation_id: OB-IMPORT-RESTART-001
source_ac: [AC-IMPORT-01]
risk: stale-persisted-running-state
scope: same-account-same-import-source
preconditions:
  process_restarted: true
  persisted_import_status: RUNNING
  active_worker_instance: false
stimulus: StartImport
must_hold:
  - a_new_import_is_accepted
  - at_most_one_active_import_exists
oracle:
  observe:
    - import_api_result
    - active_worker_count
    - persisted_task_transition
recommended_layers:
  - integration
  - device_scenario

这个对象将“应当验证什么”和“使用何种方法验证”分开：前者来自 AC 与规则，后者由测试工程化手段实现。若确实需要在生产中恢复旧任务而非启动新任务，设计决策必须在 AC 中提前确认，不能由测试 Agent 自行推定。

7.3 与 Anthropic 的结合方式

Gate1 前置需求挑战；Gate2 借鉴 plan.md、Skill、Hook 与自验证循环；Gate3 用独立 Verifier 和设备工具获取真实证据；Gate4 用分级权限与确定性异常检测实现灰度护栏。所有 Gate 使用同一组 AC、Obligation 和证据索引，避免每一层重新定义成功标准。

09 总结与研究索引

综合评价：一套强执行框架，仍需要更完整的正确性证明

这份 Playbook 最值得学习的是把 Agent 纳入一个可审查、可中止、可追踪的交付系统，而不只是使用 AI 加速编码。

端到端流程与可追溯性优势明显

六阶段、版本化交付件、触发与决策责任清晰。

工程执行自动化优势明显

Plan-first、单命令反馈、技能化与并行执行。

权限与治理优势明显

Hooks、分级权限、隔离、审批和审计。

需求完整性需加强

缺少完整的业务状态/规则/场景缺失判定机制。

独立 Oracle / Obligation需加强

自验证与 Eval 不等同于充分的业务正确性证明。

跨模块变更影响需加强

已有 Plan 和 Review 思想，但未系统定义传播图与验证选择。

最终核心主张

把“AI 生成链”升级为“可证明、可审计的交付链”

Intent → Spec → Plan → Code 的自动生成链，只有接入经确认的业务规则、可追溯的测试义务、独立验证证据、变更风险分析和分级批准机制，才可能演化为持续交付高质量软件的系统能力。
