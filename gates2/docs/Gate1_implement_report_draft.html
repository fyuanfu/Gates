2. 检查流程

① 需求定义检查检查目标、范围、Story、场景、Rule、状态、数据、契约、AC
② 技术方案检查检查方案自身质量，以及需求是否被设计完整承接
③ 测试设计检查检查 Test Case 是否完成，并覆盖 Story、AC、Rule、关键设计决策
④ 跨对象闭环检查检查 WHAT → HOW → HOW TO PROVE 是否形成闭环

3. 核心检查能力

对象 × 属性矩阵检查

对需求、设计和测试对象统一检查：完整性、明确性、一致性、可实现性、可验证性、可追溯与覆盖。

主动缺口探索

不只 Review 已写内容，还从流程、状态、规则、数据、异常、并发、依赖等空间主动寻找遗漏。

证据确认与反证搜索

大模型发现问题后必须绑定原始证据，并再次搜索是否已有其他定义，降低误报。

需求—设计—测试追溯

检查 Story、AC、Rule、设计决策、实现任务和 Test Case 之间是否形成完整覆盖关系。

6. 问题判定

候选问题

由矩阵检查或主动探索产生，不能直接进入阻断。

正式问题项

完成证据绑定与反证搜索后，确认问题真实存在。

实质影响判断

判断问题是否会迫使开发者或编码智能体作出高影响决策。

核心阻断规则：如果一个未关闭问题会显著改变用户行为、业务语义、数据语义、外部契约、关键架构、安全/隐私/合规或验收结论，则 Gate1 阻断。

阻断

关键定义缺失、多义、冲突、不可实现、不可验证、追溯链断裂。

警告

存在低风险缺口，但已有安全默认值或接受假设。

通过

不存在未关闭的高影响问题项。

7. 分阶段落地

V1：打通门禁闭环

目标先形成可运行、可解释、可阻断的完整链路。

  • 支持 PRD / Spec / 技术方案 / 测试设计输入；
  • 建立统一语义模型；
  • 覆盖 Story、AC、Rule、设计决策、Test Case；
  • 实现对象 × 属性检查；
  • 实现证据绑定、反证搜索；
  • 生成通过 / 警告 / 阻断报告。
输入 ↓ 语义模型 ↓ 检查 ↓ 问题项 ↓ 阻断判定 ↓ Gate1 Report
V2：增强主动探索

目标从“检查已有内容”升级到“主动发现遗漏”。

  • 状态空间；
  • 数据空间；
  • 异常与恢复；
  • 依赖与并发；
  • 安全与性能；
  • 兼容性与生命周期。
已定义内容检查 + 探索空间 = 更强的遗漏发现能力
V3：接入组织知识

目标让 Gate1 从通用检查升级为公司级工程门禁。

  • 领域规则库；
  • 历史缺陷模式；
  • 架构约束；
  • 安全规范；
  • 平台知识；
  • 历史设计决策。
通用 LLM 能力 + 组织知识 + 显式 Policy = 稳定门禁能力

最终实现形态

面向人的输出

HTML Gate1 报告：问题项、证据、影响、覆盖矩阵、阻断结论。

面向系统的输出

JSON 结构化结果：供 CI、Agent、质量平台消费。

门禁执行

所有阻断问题关闭后，Gate1 才允许进入编码阶段。

整体落地原则：第一版先确保“需求—设计—测试—问题判定—阻断”闭环可运行；后续再逐步扩大探索空间和知识深度，避免第一版门禁过度膨胀。
