01
Executive summary

核心认识与适用边界

Spec Kit 是一套让编码 Agent 围绕规格、设计、任务和证据开展工作的工具与流程集合。它将“直接生成代码”的开发方式变为“先固化意图，再组织实施，再对照意图收敛”。

01

以规格为研发源头

用 spec.md 定义业务行为、用户故事、验收场景和可测量成功标准。需求先于技术方案；实现细节留给 Plan。

02

以文件承载研发上下文

项目原则、技术决策、数据模型、契约、任务等以可版本化的文件组织，让 Agent 在多个研发步骤中重复使用。

03

以收敛检查遗漏

analyze 检查交付件之间的一致性；converge 检查代码相对规格是否完整。两者不等同于运行时测试全部通过。

一句话定位：Spec Kit 是规格驱动开发骨架 + AI Agent 执行约束 + 文件化研发知识；并非现成的完整企业 SDLC、测试管理平台、知识图谱或 CI/CD 发布系统。

官方能力 核心提供 Feature SDD 流程；可选扩展 提供 Bug Fix、Idea Assessment、Git / GitHub 集成以及 Workflow 等组合机制。三个业务过程彼此独立，评估想法和修复 Bug 不要求先执行完整 SDD。[S1] [S2]

先区分两类命令

终端命令：specify

负责 CLI 安装、项目初始化、扩展安装及其他工具级管理，例如 specify init、specify extension add bug。

Agent 命令：/speckit.*

在 AI 编码助手会话中调用，让 Agent 读取相关文件、产生交付件、执行任务。不同集成可显示为 /speckit-* 或其他格式。

文中统一以 /speckit.xxx 表示概念命令名；具体使用时依安装的 Agent Integration 选择正确语法，例如 Copilot 的 Skills 模式通常是 /speckit-xxx。[S2]

02
Process map

从项目初始化到实现收敛的完整流程

下面采用官方参考流程顺序：先建立项目原则，再定义需求；在存在真实歧义时加入澄清、质量检查与跨文档分析，最后完成开发和收敛。[S2]

SETUP · CLI
Init
初始化模板、脚本与 Agent 集成
01 · PROJECT
Constitution
项目级原则与强制约束
02 · FEATURE
Specify
需求、Story、AC、成功标准
03 · OPTIONAL GATE
Clarify
消除关键歧义并回写 Spec
04 · DESIGN
Plan
研究、技术方案、模型与契约
05 · OPTIONAL GATE
Checklist
审查规格本身的质量
06 · TASKS
Tasks
按 Story、依赖分解实施任务
07 · OPTIONAL GATE
Analyze
检查 Spec / Plan / Tasks 一致性
08 · EXECUTION
Implement
编码、执行规定的测试、更新任务
09 · FEEDBACK
Converge
发现遗漏，追加任务并再次实施
迭代闭环：Analyze 发现问题 → 回到对应的 Specify / Clarify / Plan / Tasks 修订；Converge 发现实现缺口 → 在 tasks.md 追加任务 → Implement → 再次 Converge。
精简流程

小范围、低歧义 Feature

Specify → Plan → Tasks → Implement → Converge，项目原则提前准备一次即可。

增强流程

生产功能与高风险变更

在标准流程中引入 Clarify、Checklist、Analyze，提高进入编码之前的质量。

不要混淆顺序与强制性：这些命令在官方参考中按顺序展示，但不是每一步都具有不可跳过的硬阻断器；例如质量检查命令属于可选质量增强，是否真正阻断由命令行为和团队治理方式共同决定。
03
Stage-by-stage

逐阶段：目标、输入、活动、输出与准出

“准出”栏包含建议的工程评审标准，用于落地时判断交付件是否可用；它不是官方已提供的统一自动化 Gate。

00
Init
环境建立

建立项目工作区和 Agent 集成

CLI 初始化负责安装文件模板、操作脚本与 Agent 集成入口；对于已有项目，使用 --here。Git 分支不是核心流程的前置条件，Git Extension 是独立可选项。[S3]

输入：新项目名称或既有代码仓库、目标 Agent 集成。
关键工作：生成 .specify/ 与 Agent 命令/Skills 配置。
核心交付：初始化的规范目录、模板、脚本与集成文件。
准出建议：模板可被命令识别、现有文件未意外覆盖。
TERMINAL / CLI 
uv tool install specify-cli
specify init --here --force --integration claude

注：--force 是在非空目录合并/覆盖时确认风险，建议先提交或备份已有文件；Windows 可明确选择 --script ps。[S3]

01
Constitution
项目级规则

定义工程原则与不可违反的约束

将架构边界、代码质量、测试纪律、体验与性能要求固化为项目 Constitution。它不是某个功能的需求，而是后续设计、检查、编码时的上层约束。

输入：团队技术规范、架构原则、质量标准。
关键工作：明确 MUST / SHOULD 规则和治理原则。
主要交付：.specify/memory/constitution.md
准出建议：条款可执行、无冲突，可在方案与代码中检查。
AGENT COMMAND 
/speckit.constitution 定义项目的架构约束、测试策略、性能与安全底线

示例规则：上传任务可恢复；相同照片重试不得重复创建逻辑资产；关键业务路径必须具有对应验证。需要区别：写入 Constitution 才构成项目约束，模板并不会自动替团队选择这些标准。

02
Specify
需求建模

将想法转成可验收的 Feature Spec

明确 What / Why，包括用户故事、验收场景、功能性需求（FR）、边界情况、关键实体、成功标准（SC）与假设；不要在这一阶段过早落入框架与代码实现细节。[S4]

输入：自然语言的需求目标、约束与用户场景。
关键工作：抽取 Actor / Action / Data / Constraint，形成可验证行为。
主要交付：spec.md；内置 checklists/requirements.md。
准出建议：Story、AC 与 FR 可辨识，重大待澄清项被明确标记。
AGENT COMMAND 
/speckit.specify 网络断开后暂停照片上传，网络恢复且符合策略后自动继续，重复重试不产生重复云端资产

官方命令允许对关键未定问题标记 NEEDS CLARIFICATION，并倾向于在可合理假设的情况下先写清假设，而不是让 Spec 因大量问题停滞。[S4]

03
Clarify
可选质量检查

消除足以影响实现方向的需求歧义

Agent 针对 Spec 的不明确点提出问题，将用户选择的结果回写到 spec.md。单轮最多 5 个针对性问题；可按范围多次执行。[S2]

输入：已存在的 spec.md、未决规则与边界。
关键工作：找出多解释点并收敛选择、记录澄清。
主要交付：更新 spec.md（并可复评内置需求清单）。
准出建议：影响范围、安全、用户行为及 Oracle 的关键歧义已解决。
AGENT COMMAND 
/speckit.clarify 重点检查网络恢复触发条件、手动暂停优先级、进程重启和去重语义
风险：如果某个问题被 Agent 直接默认推断而没有征询业务方，虽然文档看起来完整，仍可能固化错误前提。因此关键规则应明确由责任人确认。
04
Plan
技术设计

把需求转成可实施的架构和技术决策

该阶段不仅生成 plan.md，还包括 Phase 0 的研究决策和 Phase 1 的详细设计。Plan 模板含技术背景、Constitution Check、项目目录结构；技术选择应能解释理由及替代方案。[S5]

输入：spec.md、Constitution、现有代码约束。
关键工作：技术研究、方案决策、实体与状态建模、接口定义、端到端验证指南。
主要交付：plan.md、research.md、data-model.md、contracts/、quickstart.md（按适用性）。
准出建议：关键决策已确认，未知项有结论，接口/状态/验证路径明确。
AGENT COMMAND 
/speckit.plan 基于现有 Android 项目，使用 WorkManager 管理持久任务，明确上传幂等边界和进程重启恢复策略
技术设计子阶段主要问题典型交付
Phase 0 · Research未知技术点是什么？为何选方案 A 而非 B？research.md
Phase 1 · Design数据结构、状态转移、接口契约是什么？data-model.md、contracts/
Phase 1 · Guide怎样运行和验证关键用户流程？quickstart.md

技术判断：quickstart.md 是验证与上手指南，不应被误当成覆盖全部需求的自动化测试套件。

05
Checklist
可选质量检查

评估“需求本身是否足够好”

按照完整性、明确性、一致性和边界覆盖生成领域化检查表，例如上传权限、异常恢复、错误提示、安全等。检查的是规格质量，而不是代码执行通过率。[S2]

输入：spec.md 与评审关注点。
关键工作：产生挑战问题、评审缺口并回写源规格。
主要交付：checklists/*.md（自定义评审清单）。
准出建议：关键条目经评审人确认，通过项有证据链接。
AGENT COMMAND 
/speckit.checklist 检查上传网络状态、异常恢复、幂等与安全边界的需求质量
官方语义：内置 requirements.md 是 Specify 创建、Clarify 可复评的清单；checklist 生成的自定义清单由评审者负责决定是否打勾，不应让实现 Agent 自行生成后自动全部批准。
06
Tasks
可执行计划

按 User Story 与依赖拆分实施工作

读取 Spec、Plan 和相关设计文件，生成可直接执行的文件级任务。任务一般包含 Setup、Foundational、各 User Story 和 Polish 阶段，标记任务 ID、并行条件与 Story 归属。[S6]

输入：spec.md、plan.md 及适用的研究、模型、契约。
关键工作：建立依赖顺序、独立验收条件、建议 MVP 范围。
主要交付：tasks.md
准出建议：每项可执行、可定位文件、可判断完成与否。
AGENT COMMAND 
/speckit.tasks
重要边界：官方 Tasks 模板写明，测试任务通常仅在规格明确要求或用户要求时加入。不能因为生成了 tasks.md 就推断所有 AC 都配置了自动化验证。[S6]
07
Analyze
可选质量检查

编码前检查 Spec × Plan × Tasks 一致性

在 tasks.md 生成后进行只读交叉分析，识别冲突、重复、歧义、遗漏以及 Constitution 违规。报告按严重级别汇总并建议修复，但本命令不自动改写文件。[S7]

输入：spec.md、plan.md、tasks.md 和 Constitution。
关键工作：审查需求覆盖、术语统一、范围一致、任务可追踪。
主要交付：对话中的结构化分析报告；不默认新增文件。
准出建议：阻断性缺口清零，修复落实到原始责任文件。
AGENT COMMAND 
/speckit.analyze

若发现“FR-003 没有对应任务”，应回到 tasks；若发现需求定义互相矛盾，则回到 specify/clarify；若发现设计与需求不符，则回到 plan。发现问题不代表问题已经修复。

08
Implement
编码与执行

依照任务、技术设计和工程原则生成代码

Agent 按任务阶段与依赖完成代码修改，执行任务中要求的测试并更新 tasks.md 状态。开始前检查 Checklist 的勾选情况；存在未完成项时，会请求用户决定是否继续，而不是擅自改变检查表。[S2]

输入：tasks.md、plan.md、相关技术文件。
关键工作：编码、依赖处理、测试执行、记录任务完成状态。
主要交付：应用代码、测试代码、执行输出、更新后的 tasks.md。
准出建议：任务执行结束、必要测试通过、运行失败有可复现证据。
AGENT COMMAND 
/speckit.implement 先只实施 Setup、Foundational 和 User Story 1

对于较大 Feature，建议分 Story 实施和验证，避免把多阶段编码一次性塞入单个 Agent 上下文造成遗漏。

09
Converge
实现收敛

根据当前代码状态识别未履行的研发义务

以 Spec、Plan、Tasks 为实现意图来源，考虑 Constitution 的约束，对照代码检查漏实现、部分实现、冲突实现和额外行为。若有可执行缺口，只允许向 tasks.md 追加新的 Convergence 任务；本命令不直接修代码。[S8]

输入：完整 Spec/Plan/Tasks、当前代码、Constitution。
关键工作：用 FR / SC / US-AC / Plan 决策对照实现证据。
主要交付：收敛报告；有缺口时追加 tasks.md。
准出建议：报告 Converged，且独立测试与审查证据另行满足。
AGENT COMMAND 
/speckit.converge
必须保留的理解：Converge 不是 Git Diff 分析器，不根据代码历史推断差异；它检查的是当前代码对规格的满足情况。Converged 不是 Release Ready，不代表真机、复杂故障注入、容量、性能或线上灰度验证已经充分。[S8]

05
Structure & knowledge

知识如何随着文件在研发链路中流动

典型目录结构

gallery-project/ ├── .specify/ │ ├── feature.json # 活跃 Feature 定位 │ ├── memory/ │ │ └── constitution.md # 项目级工程原则 │ ├── templates/ # 研发文档模板 │ └── scripts/ # 命令辅助脚本 ├── specs/ │ └── photo-sync-retry/ │ ├── spec.md # 需求 / Story / AC │ ├── plan.md # 技术设计入口 │ ├── research.md # 选型与决策理由 │ ├── data-model.md # 实体与状态 │ ├── contracts/ # 接口契约（按需） │ ├── quickstart.md # 验证与运行指南 │ ├── checklists/ │ │ ├── requirements.md # 内置规格质量检查 │ │ └── security.md # 自定义检查（按需） │ └── tasks.md # 开发与收敛任务 └── app/ / src/ / tests/ # 实际代码与测试

文件之间的语义关系

Constitution：项目级规则对 Spec、Plan、Tasks、实现提供约束
↓
Spec：业务意图 / Story / AC / FR描述应当发生什么以及成功标准
↓
Plan + Research + Model + Contracts将业务要求映射成技术设计与决策
↓
Tasks：可执行的原子工作单元将需求与设计落实到任务及路径
↓
Source + Tests：实际实现和证据由 Implement 交付，Converge 对照检查
知识管理结论：Spec Kit 的强项是文件化、可版本化、与研发过程绑定的显式知识，例如项目原则、技术决策和领域模型。其核心并未内置完整的跨项目 RAG、关系图数据库、自动知识生命周期治理或组织级经验检索引擎。
06
Worked example

贯穿案例：Gallery 网络恢复后自动续传

以下是教学示例，用于说明从需求到代码如何逐层映射；不是直接来源于官方 Spec Kit 仓库的实际业务需求。

User Story
US-01：用户希望断网中断的照片上传在网络恢复后继续，避免重复手动发起。
Acceptance
US1/AC2：Given 已成功上传的同一逻辑照片，When 网络恢复引发重试，Then 不得生成重复云端资产。
Requirement
FR-003：同一账号及逻辑照片的重试过程需要满足去重/幂等约束。
Plan / ADR
设计：WorkManager 负责恢复调度；本地 UploadTask 持久化；服务端幂等键防止重复提交导致双资产。
Tasks
T005：网络恢复任务调度；T006：实现幂等键与状态回写；T007：覆盖重试集成测试。
Source / Tests
代码：UploadWorker / UploadRepository 等；证据：测试记录、重复资产检查、失败重试日志。
增强：Obligation
进一步结构化前置条件、刺激动作、Oracle 与验证层次，提升从 AC 到自动化测试的可执行性。建议扩展 · 非官方默认

为什么还建议补 Test Obligation？
AC 定义了业务可接受行为，但通常没有完整指定测试设施、准备数据、故障注入点、可观测信号和 Oracle 判定方式。若要求机器可执行、可审计验证，可进一步映射 AC → Test Obligation → Test Case → Evidence。这是对 Spec Kit 的工程增强，而不是它当前默认内置的验证资产模型。

Quality architecture

Spec Kit 的质量控制点与未覆盖的验证

CHECKPOINT / A

规格质量

Specify + Clarify + Checklist

关注需求是否完整、清晰、一致、可验证；关键边界和规则是否已确认。

官方主线 + 可选检查
CHECKPOINT / B

设计与任务一致性

Plan + Tasks + Analyze

关注 FR 到任务是否可追踪，设计是否违背需求/Constitution，任务是否有范围遗漏。

官方机制
CHECKPOINT / C

实现完整性

Implement + Converge

关注代码是否实现 Spec 和 Plan，以及未实现工作是否被追加回任务列表。

官方机制

为什么 Converged ≠ 测试完成 ≠ 可以发布？

验证目标Spec Kit 覆盖情况额外需要的工程能力
需求、设计、任务跨文件一致Analyze 可以执行只读检查业务评审人批准、严重问题阻断规则
实现满足已记录的意图Converge 可以识别当前代码的缺口独立验证主体、确定性检查和证据
单元、集成与端到端测试可作为任务生成并在 Implement 执行；默认深度不保证测试义务、测试资产、覆盖策略、结果汇总
Android 真机与复杂状态场景不作为完整内置测试平台设备矩阵、环境控制、弱网和进程故障注入
性能、可靠性、安全与发布守护可在 Constitution / Plan 中声明要求，但执行另需实现CI/CD、质量门禁、运行监测、灰度与回滚
常见误判：tasks.md 中一个 FR 被任务引用，只说明“已安排实现”，不意味着“已有足够测试”；converge 报告已收敛，也不意味着外部行为 Oracle 已被真实环境观测并证明。

Workflow / Preset / Bundle：如何封装团队流程

Spec Kit 当前还提供工作流与组件组合机制：可以串联 Agent 命令、Shell 步骤和人工审查节点，组合成重复可运行的流程；Preset / Bundle 用于组织模板、扩展和工作流，适合团队标准化。具体可用性、命令位置和集成能力应以安装版本的官方参考为准。[S9]

建议用法：先用原生命令完成一个真实 Feature，再决定哪些步骤自动串联、哪些必须保留人工决策，不建议在 PoC 初期一次性把所有命令包成黑盒流水线。

09
Architecture assessment

面向企业研发质量体系的架构评价

如果要将 Spec Kit 作为 AI Native 研发体系的基础，可以直接复用其上游规格与工作流机制，而把知识检索、测试义务、独立验证和发布证据作为增强层。

研发需求 / 问题输入新功能、技术改进、缺陷与业务反馈
↓
Spec Kit：规格与工程知识层Constitution · Spec · Clarify · Research · Plan · Tasks
↓
Spec Kit：Agent 执行与收敛层Analyze · Implement · Converge
↓
增强层 A：测试义务与验证契约AC → Obligation → Oracle → UT / Integration / Device
↓
增强层 B：独立验证执行与质量证据确定性测试、执行记录、制品身份、环境与源码版本绑定
↓
增强层 C：CI/CD 发布护栏发布审批、灰度监测、回滚与线上反馈闭环

适合直接复用的设计

  • Constitution：把项目“必须遵守什么”从 Prompt 中提取为稳定规则文件。
  • Spec / AC：让实现意图具有需求标识与验收行为，支持后续关联。
  • Research：记录 Decision / Rationale / Alternatives，避免只有结论没有选型依据。
  • Analyze：在编码前建立跨文档质量检查点。
  • Converge：将“有没有做完”从任务打勾转为“对当前代码与规格做一致性检查”。

需要补齐的设计

  • 知识库：结构化元数据、稳定知识 ID、全文/向量/关系检索、过期判断和跨项目复用。
  • 验证模型：将需求与可执行 Test Obligation、Oracle、测试层级、测试证据显式关联。
  • 证据可信度：报告与 Commit、运行环境、工具版本、测试输入及执行日志绑定，避免只依据 Agent 自我陈述。
  • 运行阶段：补充真机、系统环境、性能、容量、灰度和回滚验证。
技术判断：Spec Kit 更适合承担“规格与设计知识的生产、组织和消费”角色，而不是组织长期经验知识库的唯一引擎。若要建设企业研发知识系统，可以把其产出的 Spec、Decision、Model、Bug Report 当作结构化知识源。

Adoption checklist

用一个 Feature 做落地验证：最小实施清单

建议选择一个范围有限但包含状态转换与失败重试的真实功能，做一轮完整跑通和证据审查。以下是可以复制到试点记录里的清单：

流程与文件完整性

  • CLI 初始化完成；Agent 命令可正确定位当前 Feature。
  • Constitution 有可执行且被团队批准的强制规则。
  • Spec 包含 Story、AC、FR、边界场景和成功标准。
  • 研究、设计决策、数据模型和接口方案可追踪。
  • Tasks 对关键 Story 有实现任务和必要的验证任务。

质量与证据完整性

  • 关键 Clarify 问题已被业务责任人确认。
  • 自定义 Checklist 有评审结果，而非 Agent 自行全勾。
  • Analyze 的严重问题经修复后重新验证。
  • Implement 产生的测试结果能够实际复现。
  • Converge 无遗漏；独立测试/发布门禁另行通过。

建议保留的试点度量

度量项定义建议要回答的问题
需求澄清密度每 Feature 关键澄清决策数量及对实现的影响是否真的发现了模糊与遗漏？
需求任务映射覆盖可验证 FR/AC 中具有对应实施与验证任务的比例是否存在需求没落到执行层？
Analyze 阻断问题CRITICAL/HIGH 问题数和修复闭环率是否降低编码前返工风险？
Converge 轮次与缺口首次与末次检查缺口数、类型、修复轮次首次代码生成是否足够完整？
独立验证通过率关键验证义务具有有效证据的比例是否真的交付正确的软件？
最终评估标准：不是“生成了多少个 Markdown 文件”，而是需求歧义是否减少、技术决策是否可追溯、重要验证是否前移、修改后是否更容易判断真实风险，以及输出能否被后续 Feature 复用。
